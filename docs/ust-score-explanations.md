# 理解清晰度评估（U/S/T）与评分理由

清晰度评估（U/S/T）帮助你判断下一步值得澄清什么。请把数字与同一次评估的理由一起阅读；它们不是设计事实，也不替代你的判断。

## 跨 Kit 如何理解评分

U/S/T 衡量同一设计项目的清晰程度，不是发布进度、开发就绪证明或不同 Kit 之间的排行榜。评分应结合当前 Kit 的实际目的、输出契约和用户约定范围：

- U（理解度）：相关人员、情境、预期结果及范围边界是否清楚。
- S（结构化）：适用概念、责任、关系、层级与依赖是否组织一致。
- T（可验证）：结果和约束是否有该领域适用的可观察判断依据；不要求一定存在软件测试。

例如，现场作业 Kit 可以依据危险场景、处置责任及完成证据评估；不因没有页面原型或业务对象模型而扣分。一个范围明确的决策也不必先完成整套 Web App 设计。文件数量、篇幅、字段填满或模型写出的假设都不是用户确认的证据；衍生体验和示例也不能代替原设计事实。

评分理由应指出已保存的具体依据、冲突和仍未决定的内容。Kit 的 schema、方法和示例用于解释契约，不证明当前设计已包含或确认这些内容。新增不确定性时，分数可以不变或下降，不应为推动流程而补造高分。

## 查看理由与继续讨论

在支持评分理由展示的面板中，将鼠标悬停在“理解度 / 结构化 / 可验证”指标上，或用键盘聚焦指标，即可查看该维度的理由。长内容可以滚动阅读，按 Escape 关闭。具体入口见[使用指南](wiki/usage.md#查看和更新-ust)。

可以向 Agent 追问：“这项判断依据哪些已保存内容？最值得先补充的是哪个问题？”你也可以指出理由中的误解，再修改设计或补充背景。无需为了提高分数而运行全部 Bundle。

没有成功评估时，缺失结果不等于零分。评估不再匹配当前设计证据、Kit 身份或项目中的 Kit/Bundle 定义内容，或本次评分失败时，不能用旧分数作为当前依据推荐下一步；保留旧理由并标明状态，需要更新时标为待重新评估。旧版投影可能只有数字，不能据此假定理由已经生成。请在下一次正常评估后查看新结果；安装或更新插件不会自动重算项目中的旧评分。

## 理由的保存与展示

以下是供集成与内容作者参考的保存约定，普通用户无需手动编辑评分文件：

- `summary`、三个维度的 `evidence` 和 `nextGap` 各允许最多 64 KiB UTF-8。该值是异常输出的安全上限，不是写作长度要求；合法内容应完整保存并参与摘要计算，不静默截断。
- `clarity.json` 文件上限为 2 MiB，为合法字段的 JSON 转义留出空间。写入与读取使用同一限制，超限应报告失败。
- 主 Agent 工具、DSH 独立评分器和 Companion 评分提交复用验证契约，检查分数范围、身份、摘要完整性、版本和持久化一致性。
- DSH 与 Companion 的 workspace 可选 `explanation` 携带原始理由及评估提交。同分但理由变化也应刷新展示；旧评估仍标为待重新评估。

评分理由不属于 Design Files 或 KAG，不改变评分权重、时机或超时策略。摘要校验只能证明报告内容一致，不能证明模型判断正确。具体宿主可用范围见[宿主指南](wiki/hosts.md)。

维护者可运行现有的 `pnpm test:clarity-core`、`pnpm test:clarity-panel` 及独立评分器检查。验证应覆盖长中文理由、原样保存并重开、JSON 转义、各提交入口、UI 转义、旧版标记和同分理由更新；代码测试与原生宿主中的实际使用需要分别报告。
