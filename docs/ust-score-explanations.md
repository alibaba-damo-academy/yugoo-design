# UST 评分理由的保存与展示

UST 的数字与评分理由是同一份评估结果。理由不属于设计文件或 KAG，也不改变事实来源。

## 跨 Kit 如何理解评分

U/S/T 衡量同一设计项目的清晰程度，不是发布进度、开发就绪证明或不同 Kit 之间的排行榜。评分应结合当前 Kit 的实际目的、输出契约和用户约定范围：

- U（理解度）：相关人员、情境、预期结果及范围边界是否清楚。
- S（结构化）：适用概念、责任、关系、层级与依赖是否组织一致。
- T（可验证）：结果和约束是否有该领域适用的可观察判断依据；不要求一定存在软件测试。

例如，现场作业 Kit 可以依据危险场景、处置责任及完成证据评估；不因没有页面原型或业务对象模型而扣分。一个范围明确的决策也不必先完成整套 Web App 设计。文件数量、篇幅、字段填满或模型写出的假设都不是用户确认的证据；衍生体验和示例也不能代替原设计事实。

评分理由应指出已保存的具体依据、冲突和仍未决定的内容。Kit 的 schema、方法和示例用于解释契约，不证明当前设计已包含或确认这些内容。新增不确定性时，分数可以不变或下降，不应为推动流程而补造高分。

没有成功评估时，不把缺失结果显示成零分。已有评估不再匹配当前设计证据或 Kit 身份/版本时应标为待重新评估，保留其原理由而不冒称当前结论；评分失败后也不能用旧分数推荐下一步。报告摘要校验只证明报告内容一致，不证明模型的判断正确。跨 Kit 的实际评分与完整发行验收仍是待办，本说明不将源码契约提升为已验收结果。

## 理由的保存与展示

此前每维 evidence 限制 1024 UTF-8 字节，评分器超限时拒绝整份评估，导致设计产物
已发布而评分停留在旧版本；页面又只投影数字，无法查看已有理由。

本次修改：

- summary、三个维度 evidence、nextGap 均允许 64 KiB UTF-8，仅作为异常输出安全上限，
  不作为简短写作要求。正常长中文内容完整保存、完整计算 digest，不静默截断。
- clarity.json 文件上限同步为 2 MiB，覆盖各合法字段的 JSON 转义膨胀；写入与读取
  使用相同上限，避免成功保存后无法重新打开。
- 主 Agent 工具、DSH 独立评分器、Companion 评分结果提交复用相同验证契约。
  保持分数范围、身份、摘要完整性、版本与持久化一致性检查。
- DSH 与 Companion 的 workspace 返回可选 explanation，携带原始评分理由和评估提交。
  指标以“理解度 / 结构化 / 可验证”展示；鼠标悬停或键盘聚焦指标时，直接浮出
  该维度的评分理由，无额外图标或统一说明弹窗。长内容可滚动查看，Escape 关闭。
  旧评估继续标记待重新评估，不冒充当前评分。
- 同分但理由变化也会触发 workspace 展示更新；无理由的旧投影仍能显示数字。

不更改评分权重、评分时机、超时策略、Kit 或宿主应用；不自动补算现场旧评分。
此前失败的评估需要下一次正常评分才能刷新。极端超大输出仍明确失败，不能静默丢弃
或假称成功，这与此次消除正常理由的过小限制不同。

验证入口：`pnpm test:clarity-core`、`pnpm test:clarity-panel`，以及独立评分器 smoke。
包含超过原上限的中文内容、原样持久化并重开、JSON 转义、工具／评分器／Companion
提交链路、UI 安全转义、旧版标记和同分理由更新。
