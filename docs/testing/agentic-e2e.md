# Agentic E2E 测试剧本

本剧本用于语构设计系统（Yugoo Design）的开发交付与版本发布验收。测试执行 Agent 扮演用户，经真实宿主对话和产品界面驱动被测 Agent，检查实际执行、设计数据、保存重开与后续消费；不能用手工补产物、脚本模型或一张截图代替业务闭环。

这是唯一维护的剧本。运行结果写入当前任务的证据目录和工作记录，不把逐次日志写回本文，也不另建一套发布计划。入口规范见 [AGENTS.md](../../AGENTS.md)，产品机制以[架构基线](../system-design-baseline.md)、[Bundle 契约](../bundle-contract.md)及所属包源码为准。

## 执行时机和完成口径

- **每次开发交付前：** 必须完成 A 新任务、B 旧项目迁移、C Studio 创作三条主线检查，逐项记录结果。只有编译、单测或页面打开不能完成这项检查。执行过程中修复缺陷后，重跑受影响检查及其下游；同一固定候选未受影响的成功结果可以复用，必须引用原证据并说明依据。
- **发布候选：** 在最终集成版本上汇总三条主线结果，绑定源码和实际构建产物。开发源码、安装候选、已发布 npm 是不同验证边界。其他宿主的扩展矩阵单独记录，不能冒充主宿主通过，也不自动阻塞已明确限定的发布范围。
- **发布后：** 必须完成 P1 从零安装、P2 从上一正式版本升级，再完整复跑 A/B/C 中至少一条。抽样规则见下文，不能以发布前结果替代。
- `PASS` 需要实际观察与证据；`FAIL` 表示行为不符；`BLOCKED` 表示环境或能力缺失无法完成；未执行写 `NOT_RUN`。失败、阻断和未执行均不能计为通过。改变必测范围须明确记录用户或发布负责人的决定，执行者不得自行删项、降级标准或把缺陷改成预期。
- 规范、文档等不改变可执行内容的维护仍需在交付中交代 E2E 状态，可引用对相同运行产物有效的既有结果；没有有效结果就如实写未执行，不能把文档链接检查称为 E2E 通过。

## 开跑前填写一次

可以将下面的指令交给执行 Agent；版本、宿主和隔离目录必须取自本轮已确认的任务上下文，不得猜测或使用真实用户数据：

```text
请读取本仓库 AGENTS.md 和 docs/testing/agentic-e2e.md，执行真实 Agentic E2E。
阶段：<development / release-candidate / post-release>；目标：<固定源码/精确包版本>。
宿主：<已配置的测试宿主>；隔离根：<本轮专用目录>；资源上限：<时限与模型预算>。
先记录实际加载版本和执行计划，再按相应阶段运行全部必需检查。
使用产品对话和 UI 扮演用户，让宿主 Agent 完成后台工作；不要代写产物。
缺少环境或权限时记录具体阻断，不改真实用户配置，不擅自发布或扩大范围。
输出逐检查点结果、证据、未完成项和清理清单，不能只给成功摘要。
```

在现有任务记录中填写这些变量，后续提示词替换尖括号占位符：

| 变量 | 必填内容 |
| --- | --- |
| `RUN_ID` | 唯一运行标识，用于项目名、证据与清理清单 |
| `SOURCE` / `ARTIFACT` | 固定源码提交；构建来源、精确版本和包摘要；注明源码运行、安装候选或实际 npm |
| `HOST` | 宿主、版本、平台、原生模型路由和可用搜索能力；不记录凭据 |
| `KIT` | 实际加载的 Web App Kit 与四个 Bundle 的精确 pin、编译后的执行策略 |
| `ROOTS` | 独立宿主 profile、项目根、系统状态根、Studio 存储、浏览器/Electron 用户目录及端口 |
| `EVIDENCE` | 仓库外的任务证据目录，记录拥有者、引用者与清理条件 |
| `LIMITS` | 本轮总时限、单步等待上限、模型调用预算；超限保留现场并标阻断，不无限重试 |
| `PREVIOUS_VERSION` / `RELEASE_VERSION` | 发布后检查使用的上一正式版与本次精确 npm 版本，不能只记 `latest` |

使用现有受支持宿主；完整创作主线优先选择具备原生 Agent、搜索、Subagent 和 Studio 的 DSH Web。内部模型网关仅作为该宿主已配置的模型路由，不成为产品或测试者的第二个模型客户端。启动及隔离方法沿用[开发指南](../wiki/development.md#隔离-ui-与宿主验证)。仅设置 `DSH_HOME` 不足以隔离 Core `projectsRoot`、`stateRoot` 或 Electron userData。

首次启动隔离环境时确认项目列表为空；继续同轮复测时核对原测试项目身份，不清空既有证据。确认选中的构建确实被宿主加载，记录加载路径与版本；不要改真实用户的 profile、认证或项目。可以复用已校验的只读依赖和完整模型缓存，但必须记录：这不等于验证模型首次下载。模型资源缺失时分别记录结构图谱、语义检索和设计编辑能力，不能宣布整个 KAG 或产品都不可用。

**搜索预检：** 调研前确认搜索和网页读取各自可用。使用本轮指定的狗粮网关时，核实际宿主模型路由；复用已授权的正式搜索插件与配置，不另建模型客户端。记录搜索插件精确版本、实际解析路径、选中的搜索/读取提供方和凭据是否可用，不记录密钥值。通过真实宿主对话搜索一个公开主题，再读取其中一条来源，保留原生调用与结果。`web_search` 成功不代表 `web_fetch` 或 `read_page` 可用；有多个提供方时明确配置选择，不能只凭插件已加载或 key 已配置宣布通过。复用配置只覆盖本轮隔离环境，不改正式 profile。预检通过不能代替 A-RESEARCH 的计划交接、来源约束和报告验收。

**角色边界：** 测试 Agent 可以在 UI 输入需求、回答问题、修改和保存 Panel、读取日志/文件核证。被测宿主 Agent 必须通过其已安装技能、原生工具及受限工作副本完成生成和修订。测试 Agent 不替它写 canonical JSON、BPMN、评估、审查结果或 Studio 候选，不替它调用 Chrome 来完成后台创作。人工编辑只在剧本明确的用户步骤发生，并记录由谁修改。

若某步失败，不用后台 API 绕过失败的 UI 入口再计通过。可以只读诊断，保留失败后修复并重新验证原路径。运行状态轮询采用有界等待；`accepted`、`queued`、`in_progress`、`due` 都不等于完成。

## UIUX 实际操作闭环

用户界面变更必须执行这一节；范围是受影响路径及其相邻共享状态，不新增用户审批或重复完整产品审计。

1. **先审交互成本。** 用一句话明确用户目标，从正常页面入口梳理最短可用路径：用户需要理解什么、作哪些决定、在哪里操作、怎样知道完成或失败。检查是否暴露内部实现术语、引入不必要的页面或确认，以及新流程是否丢失已确认的交互。复用 [Panel UIUX 标准](../panel-uiux-standard.md)，不得以外部技能建议覆盖现有共享样式和用户确认的场景基线。
2. **技能辅助审查。** 可用 [ux-heuristics](https://github.com/wondelai/skills/tree/main/plugins/ux-design/skills/ux-heuristics) 检查可发现性、操作成本、反馈与错误恢复，用 [web-design-guidelines](https://github.com/vercel-labs/agent-skills/tree/main/skills/web-design-guidelines) 检查控件语义、键盘焦点、表单状态、主题和布局。按所用技能读取其规则；技能不可用时仍执行本节检查，不因缺少技能跳过验收。记录具体问题及影响，不以分数代替实际通过。
3. **真实点击并看屏幕。** 在 9222 Chrome（不可用时记录实际使用的浏览器）确认加载当前实现，从可见入口完成操作。操作前检查真实窗口未最小化且目标页面 `document.visibilityState === 'visible'`；若页面隐藏导致轮询暂停，先检查并恢复窗口环境，不用伪造的 visibility 事件或修改业务状态冒充实际操作。检查入口、按钮位置和文案、操作次数、成功/失败反馈；覆盖适用的取消、重试、键盘及未保存输入保留。实际查看渲染截图或屏幕，检查未样式化控件、层级、间距、对齐、溢出、可读性及相关明暗主题。DOM/计算样式用于定位原因，不能替代看屏幕；不从隐藏 URL 或 API 绕过入口缺陷。
4. **修复后重走。** 对发现的明显 UI/UX 缺陷，在所属共享组件、样式或流程中修复，再从同一可见入口重走受影响路径。新增/修正控件应检查代表性的共享使用场景；复用无变化的证据，不无限扩大测试。
5. **分开记录结果。** 在同一任务记录里写明功能结果、UIUX 结果、实际操作路径、视觉/交互发现、修复与复查证据、未测试边界。适用的 UIUX 检查未通过时，功能成功也不能把该检查点记为整体 `PASS`。浏览器阻断时写明未完成实际操作，不用编译、API 成功或静态审查填补。

**完成前的最低检查：** 实现者负责从正常入口完成下面适用项，不把基础可用性留给用户找问题。涉及 Studio 反馈时按[统一反馈映射](../panel-uiux-standard.md#studio-信息反馈)核对；没有发生或无法触发的状态写明未测，不用成功截图代表失败恢复。

| 检查 | 不通过的典型情况 |
| --- | --- |
| 入口与已有布局 | 只能靠隐藏 URL 或解释找到入口；已确认的搜索、导航、操作菜单在合并后消失或换位 |
| 控件与反馈外观 | 原生默认按钮、裸报错段落、错误主题色、遮挡或溢出；仅检查类名存在 |
| 真实状态 | 同时显示运行中和已完成；下载发起被称为已保存；校验未通过却声称可用 |
| 错误恢复 | 错误只有内部术语；无重试/修复入口；要求先丢弃修改才能继续；取消后仍被旧结果覆盖 |
| 输入与操作成本 | 切换视图丢输入、同一动作重复确认、多处保存含义不同、增加无必要的页面或决定 |

**复发缺陷必须回到共同原因。** 在当前工作记录写下：受影响路径、具体根因、原检查为什么漏过、共享修复位置、回归覆盖以及原路径复查结果。先判断是资源没有加载、选择器/主题不生效、绕过共享组件、状态契约错误，还是已有实现在集成中被覆盖；不能仅以“加一个 class”结案。可机械验证的问题加入最小有效回归，并证明能识别原缺陷；操作成本、视觉层级等仍靠实际浏览器审查。复查一个受影响的共享使用场景，复用其余未改变的证据。维护现有规范和本剧本，合并或替换重复/过时条目，不为每个问题另建清单或审批流程。

样式检查同时覆盖交互控件与错误/状态反馈。`packages/studio-ui/tests/control-style-coverage.mjs` 检查渲染节点是否命中有效的作者样式，仅用于发现明确漏口；不能证明浏览器中的最终层叠、主题、布局或交互合理性。开发交付记录应包含固定源码/实际运行构建、可见操作路径、功能结果、UIUX 结果及剩余缺陷，并链接已有证据，无须新增报告模板。

例如 C-ARCHIVE 必须从列表上的“导入”走到选择文件、错误/成功反馈和刷新重开，并查看 `…` 菜单的导出/删除控件；后端接受归档不证明入口可找到、控件有样式或用户能恢复失败。相同原则适用于 Panel 保存、Studio 编辑与 KAG 操作。

## 运行模式与 handoff 覆盖表

先读取所测 Kit 实际策略，再核下表；策略发生合法变更时维护剧本，不能为了测试修改 manifest。这里覆盖的是机制，不是把这些 Bundle 固化为所有设计任务的必经阶段。

| 检查 ID | 默认入口 | 必须观察的运行/交接 |
| --- | --- | --- |
| A-QA | `smart_questions` | `main` + `must_edit`；有效用户编辑保存前不得结清交接，保存后原会话读取真实回答 |
| A-RESEARCH | `research` | `main` + `user_continue`；先发布当前计划并等待明确继续，普通聊天不自动执行计划 |
| A-FUNCTION | `function_modules` | 默认 `subagent` + `none`；真实独立 Producer 完成校验和发布，无凭空增加的用户编辑门槛 |
| A-FLOW | `flow_design` | 默认 `subagent` + `none`；Producer 整合两个独立 BPMN，覆盖实际精确路径 Worker 委派和返回 |
| A/B-GRA | G、R、A | 原生后台评审、结果发布和前台建议处置；评审不取得设计写权限 |

省略 `execution.mode` 的默认值是 `subagent`。Producer 执行与文件 Worker 委派是两个维度：Flow 输出了两张图并不能证明 Worker 跑过。Flow 方法允许串行执行，但本剧本需要覆盖委派机制；串行成功可以单独记录，Worker 覆盖项仍未通过。宿主不支持某模式时报告能力缺口，不静默改为主 Agent 运行来补齐表格。前台 Bundle 与后台 GRA 也不是同一种 Subagent 测试。

## A：从新任务走完设计协作

### A0 新建与推荐

通过宿主正常入口发送：

```text
使用 Yugoo Design 新建 e2e-<RUN_ID>-new 项目，选择 Web App Kit。
我们是六人设计工作室，希望做一个客户反馈处理工具。客户提交修改要求，
设计师判断是否在原定范围内，需要时由项目负责人确认范围和交期。
现在不写实现代码。请先指出最重要的未知项，推荐合适的下一步及原因，
等我选择；不要替我确定业务规则，也不要一次执行所有设计。
```

检查项目身份、根目录、Kit pin 和空初始状态。推荐应针对此请求、引用当前可用能力并说明原因；不要求固定措辞或固定排序，也不能虚构不存在的 Agent/Bundle。保存推荐与用户选择记录。随后明确选择先问答，不能用测试提示中已经列全流程来冒充 Agent 的推荐。

### A-QA 用户编辑交接

```text
先运行智能提问，聚焦谁能确认新增范围以及退回补充怎样处理。
请展示问题面板，让我填写后再继续。
```

1. 核真实 `main` 执行、问题产物与 `must_edit` 待编辑状态。先不保存，只在聊天说“继续”；它不能假定问题已回答或把未编辑状态结清。
2. 在真实问题 Panel 填写适用回答：设计师可处理原范围内且不影响交期的小改；新增页面或交期影响由负责人确认；退回时保留反馈，由设计师补充再提交。对本案例确需的登录/存储问题，选择团队成员登录、持久保存。不要为凑字段伪造其他需求。
3. 保存后记录改动、项目 checkpoint 与交接结果。要求宿主复述已保存的决定，核它实际读取到了回答，而非只回显聊天提示。

通过标准：用户编辑确实保留；交接只结清一次；被测 Agent 使用保存后的事实；不会自动自答、制造确认或覆盖用户输入。

### A-RESEARCH 计划确认与实际调研

```text
请研究现有工具怎样处理“收集反馈”和“承诺执行”的区别，
以及退回补充后重新提交的交互。范围限制为两个方向、少量一手来源。
先给可调整的调研计划，等我确认再检索。
```

1. 核 `user_continue` 暂停与当前计划版本。可在计划中把一个方向改为“退回原因如何保留”；保存计划不能被当成开始调研。
2. 发送一句普通修改意见，确认它更新/讨论计划而没有误触发执行。
3. 通过真实“开始调研”动作或该版本声明的继续别名确认。观察宿主原生搜索调用、来源、方向进展、报告文件、综合结论及终态。

通过标准：执行的是最新确认计划；有实际搜索/读取来源证据，报告引用能对应来源；结果文件可打开，刷新后仍在；参考机制没有被擅自写成已确认需求。搜索不可用记阻断，不允许测试 Agent 补写报告或以模型记忆冒充检索。

### A-FUNCTION 独立 Producer 与无交接完成

```text
根据已保存的回答和调研，梳理客户反馈处理所需的功能模块。
本轮只覆盖反馈提交、范围判断、负责人确认、退回补充和状态查看。
请保留已经确认的边界，不加入自动批准或自动承诺交期。
```

核原生 Producer 身份/父子关系、实际工具调用、校验、发布和终态。主 Agent 不能自行写文件伪装独立 Producer；`handoff: none` 不应产生额外的必填问题门槛。

用户在 Panel 修改一项标题或描述，加入可识别标记 `E2E-<RUN_ID>`，保存并重新打开核对。随后要求宿主根据这次修改继续；检查来源和实际内容，不能只凭它说“已读取”通过。

### A-FLOW 文件 Worker、脚本与整合

```text
请基于已保存功能设计两条独立流程：客户反馈提交与范围确认；
负责人退回补充后重新提交。先确定共同角色和状态，再规划两张 BPMN。
宿主支持时，请将两个独立 BPMN 文件分别交给文件 Worker，
你负责整合、校验和发布。保持已有用户修改，不生成实现代码。
```

核 Producer、真实 Worker 调用及各自精确 `artifact_kind/id/file`，不得让 Worker 写别人的文件或 canonical JSON。核 `run_skill_script` 的 BPMN 校验、布局、最终校验结果及 Producer 的整合发布；测试执行者不能在外部替它跑脚本修复产物。

检查两张图均可渲染，canonical 记录指向实际文件，角色/分支符合保存的决定，无队列状态混入设计事实。记录 Worker 返回、父任务最终发布、Git checkpoint；这些不是一个“完成”标志。

### A-STATE 保存、重开与下一步

关闭再打开测试项目，核 QA 回答、调研报告、功能标记和两张 BPMN。发一个局部修改请求，例如“退回补充时必须保留原退回原因”；检查只修改受影响内容，原 ID、无关记录和用户改动仍在。

要求 Agent 推荐下一步，说明最重要缺口；测试用户明确“本轮够了，暂不扩展页面设计”。核其尊重停止/延后，不为了补满分继续生成。随后完成下方 A-UST、A-KAG、A-GRA 检查。

## A/B 共用：必须实际检查 UST、KAG、GRA

在 A 完成后执行一次，在 B 的新迁移项目中再次执行一次；不能直接复用另一个项目的结果。

| ID 后缀 | 操作 | 检查点与证据 |
| --- | --- | --- |
| UST | 对宿主说“请根据当前已保存设计更新 U/S/T，说明依据与最重要缺口，通过评估工具保存；不要为评分重新生成设计或启动 GRA。” | 观察主 Agent 实际报告工具（DSH 为 `report_design_clarity`）与成功结果；检查 `design_records/clarity.json`、项目/Kit/被评估 checkpoint 和界面一致。新设计变化后可重新评估；分数不必上升，也不以满分为通过标准。失败保留旧成功记录，不能冒充本次新评估。 |
| KAG | 查当前索引状态，陈旧时通过正常入口刷新一次，等待实际终态；查询“谁能确认新增范围”，从节点/关系回到原始设计文件。 | 核当前项目和来源版本、实际查询返回与原文；图谱详情正确、能定位源记录。记录结构索引与 embedding/语义查询的独立状态：非空图不证明语义模型可用，空检索不自动证明 KAG 故障；已知存在的目标事实必须可定位并解释查询路径。PRD/摘要不能被当作额外独立来源。 |
| GRA | 通过正常设置/工具明确触发 G、R、A 各一次，检查实际原生执行及结果；随后完成一次用户建议处置。 | 记录每类运行 ID、原生子会话/能力、输入版本、终态与结果。可复用同一 checkpoint 已完成的自动审查，不重复触发。没有发现是合法结果，但必须有实际完成记录。核主对话可用，评审本身不改 Design Files；检查结果对应当前项目。 |
| GRA-ACTION | 对已有建议先延后/拒绝一条，核没有擅自改设计；再接受一条有实际意义的建议，观察主 Agent 普通续作。 | 接受事件、原生续作、选择的工具/Bundle和最终结果分开记录；接受不等于已修改。若没有可处置建议，在隔离项目中通过用户 Panel/正常宿主创作引入一个受控矛盾，例如 QA 仍要求负责人确认，而一条功能允许设计师自行确认新增范围；保存后只重跑相关审查。清晰记录这是故意的测试修改，验证建议后经主 Agent 修复。 |

GRA 无后台能力时不能静默切同步。只在用户明确选择后测试一次前台回退，并把“回退路径通过”和“后台运行未覆盖”分别记录；不能用回退结果满足原生后台覆盖要求。触发建议后只读比较 Design Files 与原 checkpoint，系统评估/审查记录变化不算擅改设计。

KAG 视觉同时抽查：默认文字密度、定位/搜索/选择/退出、明暗切换、2D/3D 切换与工具可用；画布操作前后设计文件不变。详细颜色和布局回归复用现有浏览器测试，不在每次业务脚本中重做全套视觉评审。

## B：旧示例迁移后继续设计

固定输入为 [工作室项目交付平台示例](../../examples/design-team-delivery/README.md)。从所测固定源码复制**整个** `examples/design-team-delivery` 到新的仓库外目录，记录源提交与完整文件清单/摘要。原样保留 `project.json`、Design Files、历史记录及附属 BPMN/HTML/Markdown；不要修改仓库示例。

迁移不是复制旧项目完整运行历史。按[项目文件管理](../wiki/project-files.md)区分保留的设计事实、允许适配的内容和需要重建的派生结果。

## C：Studio 创作、保存消费与导入导出

从当前宿主入口在独立 tab/浏览器打开 Studio。只在新建/编辑 Kit 或 Bundle 时出现 AI 对话；保留外层导航、顶部信息与内部文件导航。下面所有 AI 修改必须通过屏幕上的聊天输入交给真实宿主，测试 Agent 不能改文件代演。

### C-BUNDLE 独立创作与持续编辑

1. 复制 `business_rules` 为本轮独立 Bundle；再从空白创建一个最小 Bundle，检查创建、打开、复制、编辑各自语义。不要修改已安装原版。
2. 在编辑聊天框发送：

   ```text
   请先读取此工作副本的创作方法、输出契约和已安装组件说明。
   把当前规则面板明显改为卡片列表配合选中详情的表达，突出规则标题、
   条件和结果；使用现有共享组件，保留已有记录 ID 和字段语义，
   不为了演示增加无业务依据的状态或其他填写字段。
   准备源码修改并让我预览审阅，不要自行保存或发布。
   ```

3. 核宿主实际可读创作技能、组件契约与当前副本，拥有受限编辑工具；看得到真实执行、候选 diff 和面板变化。测试者不得通过 Chrome 或 shell 替宿主生成候选。
4. 原始文件在“编辑/diff”之间切换；面板预览左侧 `panel.yaml`、右侧实时渲染，共享同一份候选状态。全局保存/还原作用一致；无效 YAML 有明确诊断，不能错误显示已保存或已验证。
5. 先还原一次候选，核未写入；再请求修改。人工编辑一个可识别文案后，通过全局保存，关闭重开，核源码与预览保留。
6. 第二轮聊天只修改一个局部，并明确保留刚才人工修改；再次保存重开。核原生 Agent 读取当前副本内容，无旧候选覆盖新修改。
7. 空白 Bundle 补齐真实方法、schema、validation、面板和预览样例，验证可保存、预览、重开；不以仅能保存不完整草稿代替可用内容。

### C-KIT 新建、挂载与编辑

1. 新建 Kit，编写 Mindset，挂载上一步 Bundle 的稳定身份；再复制一个已有 Kit，确认复制独立、原件不变。
2. 核“原始文件/挂载管理”切换，Kit 不显示一个虚构的 Bundle 面板。挂载管理左右分栏，已挂载项不重复出现在备选中，搜索仅过滤备选；添加、移除、保存、重开后声明与显示一致。
3. 通过 AI 对话修改 Kit 方法，再人工补一处文案并保存；第二轮对话读取这些改变。核挂载身份保持不变且读取该 Bundle 当前已保存内容，空 Kit 与有效可执行 Kit 不混淆。
4. 宿主断开时保留输入/未保存内容并提示连接问题；仍可使用的手工编辑要可达，不虚构 AI 成功。恢复连接后通过正式入口重新建立上下文，再继续。

### C-ARCHIVE Bundle 和 Kit 分别往返

对独立 Bundle 和含挂载内容的 Kit **各做一次**“保存 → 对象的 `…` 菜单导出 → 隔离接收环境选择文件导入 → 成功提示 → 打开/重开”：

- Kit 与 Bundle 各自列表的新建按钮旁提供“导入”，点击直接选择文件；相邻菜单可选择文件夹。取消选择不改变内容，导入成功刷新当前列表并提示成功，不增加归档页。
- 单独核验普通点击能打开系统文件选择窗口，并能取消后再次打开。自动化工具直接填入文件只证明上传处理，不能替代这个检查；文件选择拦截应限于可关闭的测试标签页。交还页面前解除拦截，或在同一测试环境的新标签页重新验证普通点击，避免留下按钮无响应的测试状态。
- Bundle 分别覆盖普通 ZIP、文件夹和裸 `SKILL.md`；只有 `SKILL.md` 是导入必需文件。缺少其他定义文件时保留为本地副本，提示缺项并可选择“AI 补齐”或“暂不补齐”。后者保留卡片“待完善”提示；前者进入原有编辑模式，聊天框带入缺项上下文，用户正常发送。不得实现另一套补齐会话或写入流程。
- 普通 Skill 的导入单位是完整目录，`SKILL.md` 仅为识别入口。用包含 `references/`、`assets/`、`scripts/` 的样本检查 ZIP 和文件夹导入；嵌套路径、相对引用、文本和二进制文件都应在保存、重开和导出后保留，不按 Bundle 定义文件白名单裁剪，也不凭空补造来源没有的附件。
- Kit 的核心文件是 `mindset.md` 和 `kit.yaml`；挂载问题在已有挂载管理中修订。选择错误类型、缺少核心文件或无法读取的 ZIP 时明确提示，允许重选，不虚构成功。
- 编辑模式中人工新建一个文件，通过全局保存、关闭重开核对；再让真实宿主 Agent 新建另一个文件，核相同文件树、diff、预览和保存流程。完整与待完善副本都可新增文件。补齐定义后重新读取，卡片警告应消失；不能把可保存草稿当作完整定义。
- 导出位于本地副本及已安装内容的 `…` 菜单，点击直接下载 ZIP，不填写来源或许可证，不检查是否存在许可证。已有随包文件照常保留；未发送对话和正在编辑的内容不丢失。
- 下载文件应可用普通压缩工具打开，保留可读的中文文件名及完整源文件；检查实际文件名、ZIP 签名和内容，再用实际下载文件导入。浏览器开始下载不等于已保存到磁盘。旧 JSON 导入的兼容检查单列，不替代 ZIP 往返。
- 导出当前已保存内容；有未保存修改时不能偷偷导出旧底稿并声称包含新修改。已安装独立 Bundle 可直接导出其当前完整内容，不应先创建副本或要求包含它的 Kit。
- 同名重复导入自动重命名新副本，不覆盖已有内容。比较方法、schema、面板、语言资源、二进制/附件和随包挂载内容；身份投影之外的原始内容应保留。UI 名字相同不能代替源码核对。
- 接收环境不借用作者工作区或安装路径；Kit 可解析其实际挂载内容。完整 Bundle 正常挂载后，通过宿主入口运行一次小任务、展示 Panel、人工修改保存后重开。不完整导入与完整可运行内容分别记录。
- 查看 Bundle 卡片的 Kit 数量标签，点击即查看挂载；不再显示重复操作。检查入口、忙碌/成功/失败反馈、按钮、菜单和弹窗沿用共享样式。

### C-CURRENT 保存消费与项目隔离

在原有编辑器完成一次普通保存，随后通过真实宿主 Agent 使用该 Kit/Bundle。
不要求发布、升级内容版本、选择 latest 或重新挂载。源码保存成功、样例预览成功、
原生 Agent 实际读取和运行成功分别记录，不能互相替代。

1. 在库中直接编辑同一 Bundle，保存后再打开应为相同身份；显式复制后修改副本，原件不变。未完成文件可保存，实际预览/执行所需内容缺失时给出具体诊断。
2. 用 Kit 创建项目，核 `design_kit/kit/` 与 `design_kit/bundles/<identity>/` 包含完整方法、schema、校验、Panel、语言和资源；宿主从这一份读取。
3. 修改库 Bundle 后，新项目取得新内容，已有项目仍使用原项目文件；关闭重开后结论不变。
4. 让 Agent 用普通文件编辑更新已有项目中的一个定义，保留用户数据与自定义；后续读取/调用使用新文件。检查真实并发冲突，不增加单独升级流程。
5. 旧项目没有项目定义树时，只能从其真实保留的内容初始化；缺失来源应报告，不能用当前库伪装恢复。

这是当前内容模型的验收，取代本地内容版本发布要求；产品 npm 发布仍走现有 GitHub Actions。

## P：发布后实际 npm 安装与抽查

本段只在产品已经通过正式 GitHub Actions 发布后执行，不触发发布、不本机 `npm publish`。步骤遵循该精确发行版本随包的[宿主安装指南](../../packages/companion/HOSTS.md)及[开始使用](../wiki/getting-started.md)，不要复制另一版本的内部命令。

### P0 固定 registry 事实与抽样选择

记录 registry 返回的 `yugoo-design@<RELEASE_VERSION>` 元数据、`dist.integrity`、依赖版本及 `latest`。从 npm 下载实际发布包，核其与 Actions 制品身份一致；不能拿本地 tarball、源码链接或构建目录代替实际 npm。若已经有更新正式版，记录当时 `latest`，不要为了测试将标签回退。

在业务复跑**之前**确定一条链路和执行环境：

1. 优先本次改动直接涉及、修复过失败或上次未覆盖的链路；出现高风险变更时不能随机避开它。
2. 风险相当时优先轮换最长未测链路；仍相同时，可对候选 ID 的固定排序以 `RELEASE_VERSION + SOURCE` 为种子做可复现抽选，记录算法、种子、候选和结果。也可记录负责人的显式选择；“随机”不是强制要求。
3. 选择运行在全新安装或升级后的环境，记录原因；两个环境都必须做下列安装基本检查，至少一个环境完成所选业务链路全部检查点及前置条件。
4. C 若仍有未通过的保存消费或项目隔离项，仍如实报告，不得换抽一条更容易通过的来掩盖。抽样失败先修复/报告，不靠换样本凑成功。

### P1 从零安装

使用没有 Yugoo 登记、runtime 或开发源码依赖的独立宿主 profile，并隔离 npm 缓存与安装根。允许复用受支持的 Node 与完整模型缓存，但记录复用范围。

把正常安装提示词交给该宿主 Agent，明确只安装 `RELEASE_VERSION`。核 registry 包获取、安装文件、版本与摘要、宿主注册/导入、激活/必要重启、实际服务加载路径分别成功。确认无需开发机私有路径，默认 Kit 与创作资源可读；创建一个小项目，打开 Panel，编辑保存后重开。检查模型准备状态与可用能力，不把下载失败掩盖为全部可用。

### P2 从上一正式版升级

在另一独立环境先从 npm 正常安装 `PREVIOUS_VERSION`，创建并保存一个项目和可用的 Studio 副本。记录内容、ID、Kit/Bundle pin、配置与来源摘要；旧版本没有 Studio 副本能力时记录事实，不伪造旧数据。

经同一宿主的正常更新路径升级到 `RELEASE_VERSION`，完成要求的原生导入/重载/重启，核**实际运行**的新版本，而不仅是下载目录。打开原项目和旧副本，核用户数据、身份、固定内容引用仍正确；执行一次局部修改、保存重开。确认失效旧进程/旧路径没有继续接管请求，Node 选择与宿主连接正常。不要“先清空数据再升级”，也不要通过手改 manifest 或移动包伪造升级成功。

### P3 至少一条业务主线完整复跑

在 P0 选定的新 npm 环境执行 A、B、C 中至少一条，使用新的 `RUN_ID` 并保留实际原生证据。A/B 的 UST、KAG、GRA 检查仍必需，C 的 AI 第二轮、Kit/Bundle 两种归档及保存消费、项目隔离项不能缩成一个页面 smoke。另一安装环境保留 P1/P2 最短保存重开证据即可。

发布后结果应写成“全新安装：…；升级：…；抽查链路/环境：…；未覆盖：…”。发布成功不意味着 P1/P2/P3 成功；失败影响安装或数据时及时向发布负责人报告，不能因版本已上线而关闭测试。

## 结果记录、维护和复用

每轮在现有任务证据目录保存一份结果表，不新增产品运行状态或持久化 authority：

