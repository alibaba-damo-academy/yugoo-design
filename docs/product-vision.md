# 产品理念：帮助人想清楚、说出来，与 AI 对齐

[English](product-vision.en.md)

语构设计系统（Yugoo Design）的产品哲学是：**让人理解，让人思考，让人表达，与人对齐。**

**Not vibe, but intent.** 让人的意图能够进入、影响并持续修正设计，是我们选择交互方式与判断产品价值的依据。意图不必在开始时就完整明确；人也会在看到方案、比较选择和体验场景的过程中逐渐想清楚。

本文介绍产品定位、设计原则和演进方向。声明式面板、A2UI、共享推进指导及知识审查已有实现基础；具体可用功能见[宿主指南](wiki/hosts.md)与[版本说明](wiki/preview-status.md)。Studio 的完整 AI 辅助创作体验仍是演进方向，跨领域方法也需要通过实际使用不断检验。

## 1. 最核心的价值

> 帮助人把模糊的想法，变成自己能够理解、判断、修改，并逐步确认的设计。

用户带来的往往不是完整需求，而是目标、困惑、例子、局部偏好和尚未形成的判断。系统的核心不是催促用户把所有问题回答完，也不只是更快地产出文档，而是帮助人想清楚、说出来，让人与 AI 对齐。

Kit 可以让 AI 像具有专业知识、能够使用多种交流工具的咨询师一样，理解处境、查找依据、呈现选择、解释取舍，并根据人的回应修正理解；也可以定义在明确授权范围内连续完成多项成果、再集中请人审阅的专家。Mindset 定义专家的身份、个性、思考方式与特殊考虑，Bundle 提供工具箱。协作风格可以不同，但都应让人的判断能进入设计，不替人决定未授权的目标和价值取舍。

产物是双方共同思考的对象。它既可以是文档，也可以是问题卡片、比较表、流程图、页面原型或自由白板。重要的不是产物数量，而是用户能否通过它发现“这正是我的意思”或“这里不是我想要的”。

这里的“对齐”指在具体任务中形成可检查、可修正的共同理解，不是宣称模型已经具备普遍正确性。

### 什么任务需要这样的协作

当结果取决于人的偏好、实际处境、场外信息或价值取舍，而这些信息不能从现有材料中充分得知时，人的参与会实质改变结果。AI 可以生成团队报销工具，但报销单提交后能否修改、审批人怎样确定，需要你参与表达和判断。AI 也可以建立排班优化模型，但哪些班次不能连排、哪些业务例外必须保留，需要了解实际工作的人补充和确认。

这类任务不以代码量或问题大小划界。一个高度个性化的小工具同样可能需要深入协作；一个输入和评价标准已经明确的大任务，则可能适合更多自动执行。系统应把人的参与放在能补充信息、形成判断、改变结果的地方，避免为了保持“人在回路中（Human-in-the-loop, HITL）”而增加无意义的确认。

### 四个相互连接的目的

- **理解**：看懂当前方案、它的依据，以及尚不确定的部分。
- **思考**：借助专业方法、具体表达和不同选择，发现自己原来没有想清楚的问题。
- **表达**：通过对话、操作面板或修改设计，把偏好、约束和取舍准确带入方案。
- **对齐**：让人的回应改变 AI 的理解和后续行动，并能检查这种改变是否真正进入了共同设计。

我们欢迎自动化带来的效率与探索空间。需要保留的是人有意义地参与和影响结果的能力，而不是要求所有工作都由人逐项确认。

## 2. 交互：让人能够回应，而不只是要求人回答

用户的真实反馈提供了一个关键线索：有些问题说得不明白或过于琐碎；另一些问题虽然能听懂，但在没有看到产品、没有开始使用之前，用户不知道如何回答，或者希望先简化、以后再补充。

这不一定是用户缺少配合，也可能是交流方式选择错了。系统应根据当前障碍选择表达方式：

- 用户听不懂：换成具体场景、熟悉的语言和例子。
- 用户不知道如何取舍：展示少量有意义的方案，解释各自影响。
- 用户需要先看见：给出可讨论的草图、示例或原型，再根据回应修正。
- 用户希望先简化：在合适范围采用可撤回的暂定方案，并保留尚未决定的问题。
- 某项决定确实必须由用户作出：提出有依据、有针对性的澄清，不用 AI 的猜测代替。

基本节奏是“表达想法 → 看见具体表达 → 判断或修改 → 更新共同理解”，但它不是必须逐步完成的固定工作流。Agent 应根据现场和用户意图选择下一步，而不是强迫用户走完所有 Bundle。

看见不等于理解，点击确认也不必然意味着理解一致。关键是用户能否说明自己的取舍，并纠正 AI 的误解。

## 3. 各层分别承载什么

### 三个核心机制

**可交互展开、缺口驱动推进、结构化整合与校准**，共同构成系统的实践方法。它们持续往返，不是只能向前通过一次的三个阶段。

| 核心机制 | 帮助人和 AI 做什么 | 当前技术对应 |
| --- | --- | --- |
| 可交互展开 | 把一个问题展开成可以深入判断和修改的设计维度，既看清细节，也能表达具体取舍 | 设计面板（Design Panel）、声明式 UI 与 A2UI；设计技能包（Bundle）承载相应方法、数据契约、校验和执行声明 |
| 缺口驱动推进（Gap-driven Agent Loop） | 根据当前目标、已有证据和未解决的问题，判断下一步值得做什么，再根据结果重新判断 | 共享 Core 的推进指导与评估，领域主提示词（Mindset）的专业校准，以及理解度、结构化、可验证性的 U/S/T 评估 |
| 结构化整合与校准 | 连接分散设计，发现冲突、知识疑点和未决取舍，持续检查整体是否符合人的实际意图 | 知识图谱（KAG）提供可追溯关联，主动审查（GRA）提供一致性审查、知识反思与意图对齐建议 |

**信息切片（Information Slice）** 是对一个可独立推敲的设计维度的比喻。例如应用的功能、流程、规则、数据和页面，可以分别展开为可交互的结果。AI 可以提出草案，人可以直接设计，也可以修改 AI 的结果；面板与 Agent 围绕同一份保存后的设计继续工作。切片是理解设计的方式，不是新增文件格式，也不要求所有 Bundle 都必须有面板。

**缺口必须相对于当前目标判断。** 它可能是缺少一个事实、尚未作出的取舍、未验证的假设，或新旧决定之间的矛盾。下一步可以是问一个更有用的问题、查找依据、给出可比较的方案，也可以重访已经展开的设计；空字段和未运行的 Bundle 本身不是必须补齐的缺口。用户可以拒绝、延后、简化或改变方向，当前用途已经满足时也应能够停止。

U/S/T 为这些判断提供有依据的启发式线索，不是客观完成率、阶段门槛、跨领域排名或正确性证明。分数应连同理由、适用范围及尚未解决的问题一起理解；随着目标变化或新证据出现，分数可能下降。需要优化的是有意义的推进，而不是让数字不断上涨。

**整合也不是单纯汇总。** 它需要保留依据和未决事项，发现局部修改对其他部分的影响，让共同设计在整体上可理解、可检查、可继续修订。整合后的 PRD 或其他交接成果是派生表达，不替代原有设计事实。KAG/GRA 能帮助校准，却不能保证结果正确、自洽或符合现实；建议仍需要查证、判断及实际修订。

三种核心作用需要共同成立，具体技术可以演进。KAG 暂时不可用时，仍可依据设计文件继续工作、查找关联并整合方案。

### 支撑条件与增强机制

人和 AI 能围绕同一份设计继续工作、人的判断能实际影响后续行动，是上述机制成立的前提。项目存储和版本记录支持延续与追溯；专业方法包提供领域知识；场景体验把切片与关联带入具体情境，帮助人判断；Studio 支持这些方法与表达的管理和创作。它们很重要，但不需要再各自列为与三个核心机制并列的产品哲学。

| 层次 | 产品职责 | 不应退化成 |
| --- | --- | --- |
| 设计系统 | 维持人与 AI 的连续协作，支持查看、修改、保存、继续及审查 | 固定的软件文档生产流水线 |
| 设计套件（Kit） | 用领域主提示词和 Bundle 组合一类领域的专业知识、方法、判断标准与能力 | 一组互不关联的提示词 |
| Bundle | 一项聚焦的专业能力，结合 Skill 方法、资源、产物契约、校验与交互表达 | 把一个单点能力等同于完整的顾问式协作 |
| Design Panel | 让人查看、比较、操作和修正共同产物 | 只读结果展示窗或重复的聊天入口 |
| GRA | 从独立视角暴露疑点，支持后续查证、修订和澄清 | 自动认证正确性的盖章流程 |
| 设计工作室（Studio） | 帮助创作者把专业方法做成可试用、可修改、可复用的 Kit / Bundle | 要求所有专业人士先学会工程配置的管理后台 |

领域方法、资源和规则由 Bundle 自包含维护；特殊前端编辑器通过既有 Provider / Panel 扩展接入。这样可以在不同宿主中复用专业能力，而无需将领域逻辑分散到 Core 或每个宿主中。

Bundle 是专家可以调用的一项工具；Kit 与 Mindset 组织领域思考方法及工具箱，结合共享推进指导形成连贯体验。咨询式专家可以持续讨论、解释取舍和选择下一步；其他风格也可以依据用户授权连续产出，再通过面板集中对齐。

Web App Kit 是首个深入实践的领域应用。框架不应把“页面”“PRD”或一组固定的软件分面写成所有 Kit 都必须具有的概念。其他领域的专业方法由相应 Kit 表达，不提前制造一套覆盖所有领域的通用流程。

## 4. Studio：由 AI 辅助创建 Kit 和 Bundle

### 创作者先表达专业意图，系统再辅助形成技术结构

创建 Kit / Bundle 的过程本身也应体现同一理念：帮助创作者把脑中的方法变成能够理解、判断和修改的东西。AI 辅助创作是 Studio 的核心交互方向，不只是配置页旁边附加一个问答框。

创作者可以从这些自然问题出发：想帮助谁？帮助他想清楚什么？有哪些资料、案例或现成 Skill？什么表达形式便于他判断？什么算做得好？哪些决定不能替他做？这些是理解线索，不是要求一次填完的问卷。

AI 可以协助：

- 梳理领域目标、适用边界、知识依据和方法，提出 Kit 的组合方式。
- 把一个专业活动组织成 Bundle，解释需要什么输入、形成什么产物、如何与人交互。
- 复用或适配已有 Skill、示例和组件，而不是所有方法都从零发明。
- 辅助生成必要的声明、Schema、验证规则与界面配置，让创作者按需查看技术细节。
- 通过预览、试用和反馈发现方法或表达的问题，修改后再次验证。

一种期望的创作体验是：

> 描述方法或提供已有材料 → AI 提出可理解的草案 → 创作者查看并修改 → 在样例中试用 → 根据反馈修正 → 确认方法适用后保存，并挂载到 Kit。

创作方式应能适应手头已有的材料。单独创建 Bundle、组合已有 Bundle 成 Kit、适配外部 Skill，都可以从已有成果继续，无需重复走完整流程。

### “无痛”是降低技术翻译成本，不是取消专业判断

普通创作者不应先理解内部字段和宿主接口才有能力表达方法；同时，AI 生成的配置也必须可检查、可修改，不能成为新的黑盒。特殊交互可能仍需可信的代码组件，不承诺任意界面都能自动、无代码地实现。

AI 提出的专业规则和评价标准需要创作者判断是否合适。源码可以先导入、保存并逐步补全；使用外部工具或分享内容时，仍需核对实际依赖、兼容性、权限和已有许可说明。导入材料不等于授权执行其中的脚本。

延续“谁生成，谁校验并依据反馈修复”的原则。结构校验通过只能证明结构符合契约，不能证明专业方法有效或用户真的看懂；预览、真实使用反馈与专业评价仍有独立意义。

目标是让专业人士能够制作适合自己领域的交互式工具与协作体验，而不必先成为平台开发者。现阶段可利用 Studio 的查看、编辑和预览能力辅助创作，具体操作见[Studio 指南](wiki/usage.md#6-studio查看定制和检验套件)。

## 5. 声明式面板与 A2UI：选择合适的表达

引入 A2UI 的产品动机，是让 AI 的专业能力能够以多维形式呈现，并让人的回应真正影响后续理解。它不只是把文字答案换成卡片。

例如，比较方案可以用对照表，讨论过程可以用图，调整优先级可以用可操作的列表。选择的依据应是“用户怎样更容易理解和回应”，而不是界面是否新颖。

稳定、成熟的编辑器仍然有价值；不需要把所有现有 Panel 都替换为动态生成 UI。声明式面板与 A2UI 是实现手段，不是每个 Bundle 的强制要求，也不是跨宿主接入的前置条件。

无论采用哪种表达，用户的操作都需要进入同一个可继续的设计上下文。不能一套界面展示临时状态、另一套文件保存不同事实，也不能让 AI 忽略用户刚刚保存的修改。具体技术方案仍应复用既有项目、文件和保存机制。

## 6. GRA：让疑点可见，而不是让输出显得更可信

完整文档、漂亮页面和流畅解释容易掩盖理解不足。这正是引入 GRA 的重要产品动机：在共同产物逐步成形时，持续发现值得重新讨论的问题。

- **一致性审查（Grounding）**：检查跨设计文件的一致性，提出相应修订建议。
- **知识反思（Reflection）**：反思当前设计在知识层面是否存在疑点或不合理之处，推导是否需要外部研究。
- **意图对齐（Alignment）**：发现尚未澄清、需要用户作出判断的模糊项，提出针对性问题。

三者是独立审查视角，不是层层依赖的审批流水线。设计文件是事实入口，KAG 或状态摘要辅助检索；接受建议后，还需要修订实际设计。审查针对可定位的已完成版本，尚未发布的修改暂不纳入。工作进行时可审查哪些版本，以及如何处理建议，见[知识关联与审查契约](system-design-baseline.md#grounding-reflection-and-alignment)。

GRA 的输出应帮助用户看到哪里需要查证、修改或决定，而不是不断生成新任务。审查也会遗漏问题，多个视角可能共享错误假设，因此不能用“已审查”承诺结果正确。

结果表达也要保留必要的依据和不确定性：哪些来自已有材料，哪些是暂定方案，哪些需要用户决定。该原则不意味着给所有 Bundle 增加统一字段，或把每个推断都变成强制确认。

## 7. 模型进步、跨宿主与开源

### 保留用户价值，不固守技术脚手架

随着模型增强，某些提示词补丁、手动编排或专用工具可能不再必要。系统应利用宿主和模型的原生能力，并删去失去价值的复杂性，而不是为了维持现有架构限制 Agent。

需要守住的是：专业方法能够被使用，用户能够理解并修改表达，已作出的修订能够延续，疑点能够被看见。跨 DSH、Codex、Claude Code 等宿主的目标，是让这些能力可以复用，不是重新建造一个 Agent Runtime，也不承诺所有宿主的 UI 与原生能力完全相同。

Computer use 等能力可以服务于查看设计效果、操作设计表达或理解已有产品，但不会自动把本系统的职责扩张为软件开发或业务功能测试。技术能力增强应服从产品目标。

### 通过开放使用探索应用边界

开源不仅是分发代码，也是让不同领域的人带着自己的知识、方法和问题进入系统，检验 Kit / Bundle 能否承载我们没有预设的专业活动。

应用边界可以开放，核心职责仍需收敛：帮助人表达、理解、修改和确认。不能因为未来可能覆盖更多领域，就提前建立庞大的通用平台；也不能把 Web App 的成功自动当成跨领域有效性的证明。

长期有价值的积累可能来自可复用的专业方法、真实使用反馈和创作者实践。跨宿主、A2UI、文件结构或开源本身并不自动构成竞争优势；这种优势仍需由实际体验证明。

## 8. 用什么判断演进是否有效

判断一次改动是否值得做，优先看：

- 用户能否更清楚地说出目标和取舍，而不是仅仅更快拿到文件。
- 用户遇到无法回答的问题时，是否获得了有助于判断的表达。
- 用户能否发现并纠正误解，修改后是否在后续工作中得到保留。
- 尚未确定的内容是否可识别，GRA 是否带来有用提醒而非额外负担。
- 下一步建议能否说明它解决哪个当前问题；用户拒绝、延后或改变方向后，系统是否相应调整。
- 设计满足当前用途时能否结束或交接，而不是为了分数、面板数量或模板完整性继续扩展。
- 创作者能否更少依赖核心开发者，把自己的方法做成可试用的 Kit / Bundle。
- 更换宿主或引入新领域时，是否复用已有能力，而不复制领域逻辑或增加重复状态。

这些是评价方向，不是已经取得的指标结果，也不要求把它们变成一个新的综合分数。最终希望用户能够说：

> 我原来不知道自己想要什么，但跟它一起做完之后，我想清楚了，而且这个结果确实是我的意思。
