# 故障排查

排查语构设计系统（Yugoo Design）的问题时，先确认已安装的插件版本、宿主版本及操作系统，再找到失败的步骤。安装入口见[宿主兼容](hosts.md)；需要反馈时使用[问题反馈](support.md)。源码中的修复需要更新插件后才能使用。

## 先确定停在哪一步

| 现象 | 先检查 | 下一步 |
| --- | --- | --- |
| 包已安装，但 Skill 或工具不出现 | 原生插件登记、启用状态、是否按指南重启宿主 | 查看该宿主的安装入口，核对实际登记路径 |
| 工具可见，但会话未连接 | 当前原生会话、连接状态、服务是否仍运行 | 在原会话重新打开；不要复制另一会话的连接配置 |
| 已连接，但没有设计面板内容 | 项目选择、项目内 Kit/Bundle 文件、是否已有结果 | 查看项目状态，区分空项目和内容缺失 |
| 保存提示校验或冲突 | 字段诊断、最新项目版本、其他正在进行的修改 | 保留编辑内容，按下方保存故障处理 |
| 保存成功，但 AI 没继续 | 原生续作是否接受、等待输入或执行状态 | 检查原会话，必要时明确请求基于已保存结果继续 |
| Studio 界面可见，但试运行不开始 | 原生连接检查与上一次运行状态 | 检查连接；未知运行不要反复启动 |
| 已保存或审查完成，但分数和下一步没变化 | 评估所对应的项目、版本、范围及失败状态 | 将清晰度评估与保存、GRA 分开检查 |

包安装、原生登记、MCP 连接、执行和保存是独立步骤。报告具体失败阶段，避免只描述“不能用”。

## 安装或原生登记失败

按所安装版本的[宿主指南](../../packages/companion/HOSTS.md)，确认 Node 环境、安装目录、宿主版本和登记方式。长期保留已登记的 npm 目录，宿主可能引用其中的绝对路径；移动目录后仅重启 UI 不会修复登记。

CLI 安装版可按[Companion 指南](../../packages/companion/README.md#npm-candidate-and-native-installation-boundary)运行 `yugoo-design --help`，再查看当前版本的 `check-runtime` 用法。它检查安装目录的运行时依赖；宿主登记、模型加载和 KAG/GRA 仍需分别检查。桌面预览按随包材料处理，不照搬 CLI 命令。

出现缺少依赖、未知平台、原生库加载失败或版本冲突时，保存准确诊断与架构信息，使用该宿主支持的修复或更新路径。不要覆盖已存在的插件登记，或临时关闭校验来通过安装。

如果决定停用或卸载，先按[宿主移除说明](../../packages/companion/HOSTS.md#disable-uninstall-and-retained-files)处理原生登记与单独连接器，保留设计项目、匹配回执和仍被引用的 runtime。直接删除安装目录或状态目录不是通用修复步骤。

首发本地向量化使用 CPU，不要求先配置 GPU。若失败发生在额外的 CUDA 依赖下载，按[CPU 安装方式](../../packages/companion/HOSTS.md#agent-led-installation-and-updates)在获取包之前设置 `ONNXRUNTIME_NODE_INSTALL_CUDA=skip`，保留正常安装脚本。不要用全局跳过脚本代替运行依赖安装，也不要把一次依赖加载成功视为语义索引已可用。

## 会话或浏览器连接失效

确认原始宿主会话仍可用，以及 Companion 服务对应同一宿主、会话和项目。使用原会话提供的页面入口重新打开；服务停止或宿主重启后，旧页面链接不一定有效。

可在原会话发送：

```text
请核对当前项目的 Companion 是否仍可连接。
若服务已经停止，请用当前会话重新打开同一项目的面板，使用本次返回的新连接。
保留已保存设计，不重建项目、不重装插件、不重跑 Bundle。
先读真实保存状态，再继续我的任务；不要重复发送状态不明的旧消息。
```

遇到 `fetch failed` 或 HTTP 502，先检查服务是否仍在运行、地址是否为本次打开返回的地址，再检查页面与宿主连接。WorkBuddy 当前服务会在空闲一小时后回收，最长运行四小时；其他宿主见各自指南。服务关闭后项目文件仍保留，但旧连接文件中的地址可能已经失效。

页面访问被拒绝时，核对是否使用当前入口和支持的浏览器。连接 URL 可能携带授权信息，不应公开粘贴。不要把拒绝访问变成关闭认证、Origin 或 frame 检查；接入与页面访问规则见[连接契约](../../packages/companion/HOSTS.md#connection-page-presentation-and-access)。

发送后仍显示等待或状态不明时，先在原会话检查消息是否已被消费。未得到确认不代表一定未发送；重复提交可能造成重复任务。只读页面刷新也不会重放保存或消息提交。

## 项目已选，但面板没有结果

DSH 使用 `/yugoo status`；Companion 通过已安装的 `yugoo` Skill 或共享项目入口查看状态。确认：

1. 当前会话选择了预期设计项目。
2. 项目自己的 `design_kit` 中，Kit/Bundle 方法、定义和资源可读取；尚未形成此目录的旧格式项目需保留真实原内容。
3. 所查看的 Bundle 已产生并保存设计结果；空项目不是渲染失败。
4. 页面使用的当前连接没有仍绑定另一项目。

Kit/Bundle 不可解析时见[项目内容恢复](kit-sharing.md#更新与恢复项目内容)。缺少声明或 schema 错误按实际项目文件修复；已有项目源不能悄悄回退到内容库。旧格式项目只从其真实保留的原 Kit/Bundle 初始化，换成同名新版不等于恢复。此文件机制需安装版包含相应运行时。

## 保存失败、冲突或重开结果不同

| 反馈 | 如何处理 |
| --- | --- |
| 字段/schema/validation 错误 | 保留待保存内容，按定位的字段修正，再保存；不要直接写项目 JSON 绕过校验 |
| 基线已变更、并发或过期版本 | 保存自己的修改记录，读取最新内容并核对差异，再通过正常面板或 Bundle 修订；不要盲目覆盖 |
| 已提交，但 journal/diff 等后续处理未完成 | 保留已提交版本与失败阶段，让 Agent 按原收据处理后续事实；不要再次改写已提交内容 |
| 保存成功，刷新后仍是旧值 | 核对项目、Bundle 和版本，确认保存的是正常 Design Panel，而非 Studio 样例或试运行的“演示保存” |

保存与后续事实的职责见[项目持久化契约](../system-design-baseline.md#design-projects-and-persistence)。重开要检查真实字段和相关产物，不只看成功提示。不要删别人的锁、修改 Git 配置或清空项目来掩盖失败。

## 模型、搜索或原生执行失败

先在宿主核对其已有生成模型和搜索配置。对话、设计生成和审查使用宿主的模型、凭据和工具；工具清单存在、任务已排队和产物文件出现都不能独立证明原生任务成功完成。

记录是否停在生成、等待用户、执行、校验或发布。Producer/Worker 能力按[宿主兼容](hosts.md)判断；无嵌套 Worker 不代表所有 Bundle 都无法执行，选定执行者可以在获准范围内串行完成。请求的执行位置不受支持时，按明确诊断处理。

模型调用失败不会把未生成的内容变成设计事实，也不应由另一个模型 Client 冒充宿主完成。使用合成输入复现，不公开凭据、完整认证 URL 或真实私密会话。

## KAG 或主动审查没有结果

先区分知识图谱（KAG）投影状态和主动审查（GRA）状态。检查项目是否已有已发布的独立设计文件、图谱是否正在恢复、宿主是否支持后台审查，以及自主审查是否被关闭。

已检查的千问办公 `1.3.2-26101704` 在桌面集成中关闭后台 Agent，不能用普通重启或修改 `.env` 承诺恢复。WorkBuddy `5.8.3` 的用户实测中，原生异步评审仍占用主对话，也采用同一降级原则。没有可用的后台体验不等于不能评审：可选择关闭自动 GRA 并保留手动检查，或明确同意在主对话同步完成本次评审；未选择时不改策略、不运行。版本与实际验证范围见[后台能力与评审降级](hosts.md#后台能力与评审降级)。U/S/T 和 KAG 分别检查，不从 GRA 的后台状态推断其成败。

| KAG 状态或提示 | 含义与处理 |
| --- | --- |
| `current` 且 `freshness: matching` | 已有匹配版本，直接复用 |
| `due` / 陈旧 | 需要更新，但不代表任务已启动；可以明确请求刷新一次 |
| `queued` / `running` | 已排队或正在运行；保留状态，继续主任务，不忙轮询 |
| `knowledge-store-not-open` | 当前服务还未打开知识存储，不等于没有历史索引；正常打开图谱/查询后再确认，勿先删库重建 |
| `failed` / 锁或模型错误 | 保留上一完整版本，按具体诊断处理占用或依赖，再明确重试；不清空项目记录 |
| 图谱状态暂不可确认 | 先核对服务与连接；当前显示的旧图不能当作最新版本 |

语义索引还依赖本地 CPU 运行库与该版本的向量化模型。分别核对运行依赖、模型版本与完整缓存，以及是否允许下载模型；npm 包已取得或数据库已打开，不代表这些条件都已满足。[模型准备与离线限制](../../packages/companion/README.md#local-embedding-model-preparation)列出缓存位置和实际支持的入口，不能把 CLI 下载参数当成 WorkBuddy 的 MCP 参数。若显式禁用 Embedding，只保留结构投影与依据，不应报告完整语义 KAG 已验证；具体开关按所安装版本的指南使用。

KAG 读取超时、暂时不可用或内容陈旧时仍可从设计文件继续工作；不能据此声称审查已使用匹配的图谱。审查队列完成和建议生成也不证明每个视角都消费了 KAG。排查时记录项目版本、审查状态与相关诊断；没有新证据时，不必反复要求提出同一建议。职责见[知识关联与审查](concepts.md#知识关联与审查)。

## 清晰度或下一步建议没有更新

清晰度评估（U/S/T）、面板保存和主动审查（GRA）是不同结果。保存成功说明修改已进入设计；GRA 完成说明相应审查结束，均不能单独证明已有当前版本的清晰度评估。

先请原会话核对当前项目、Kit、已保存版本与本轮目标，再确认主智能体（Main Agent）是否收到并处理了本次保存差异，以及是否成功通过 `report_design_clarity` 报告该版本的评估。相同输入已有有效评估时可直接复用，不要求重复调用。没有评估不等于零分，失败或旧版本也不应被当成当前结果。不要为刷新分数重新生成或发布已经保存的设计。

可以直接说：“请根据当前已保存设计更新并持久化 U/S/T，报告写入结果和所依据版本；不要重跑设计或评审。”最近一次有效结果保存在 `design_records/clarity.json`，新评估失败不应清空旧分数。字段与 Git 历史见[项目记录说明](project-files.md#ust-具体记在哪里)。若旧插件仍要求反查原生主调用才能报告，先核对安装版本，不让使用 Agent 扫描宿主日志或改源码绕过。

若 AI 不解释当前缺口，或反复推荐已经完成、拒绝、延后的工作，可以指出本轮目的和刚刚改变的规则，请它据当前证据重新判断。新信息可能让分数下降；关键是建议是否响应真实变化。仍无法闭环时，反馈准确版本、操作顺序、期望建议与实际回应，避免公开完整私密会话。概念说明见[清晰度与建议](concepts.md#清晰度评估与下一步建议)。

## Studio 预览或试运行异常

- **没有可用样例：** 检查声明式 Bundle 的 `reference/preview.json`，以及该版本支持的初始值或显式样例输入。实际样例必须符合 schema，图表/报告等引用需有可读取资源；无效样例会报错，不自动补成一份结果。原生面板目前不提供此 YAML 预览，不能仅凭 renderer 已注册推断 Studio 可以显示。作者按[样例规范](extending.md#样例与验证)维护。
- **YAML 校验失败：** 按组件、属性和数据绑定诊断修订。先查看[组件目录和作者契约](extending.md#panel-选择)，不根据熟悉的 UI 框架猜组件名。
- **缺少编辑或试运行入口：** 核对已安装版本和该宿主支持的功能。源码 demo 提供的入口不一定包含在当前安装版中。
- **提示先保存或内容已变更：** 保留未保存输入，核对当前对象与最新源码，解决实际并发修改后再保存和试运行。保存使用内部修订检测冲突，不要求先发布本地版本或确认内容。
- **排队、未知或无法停止：** 保留运行记录，检查原生宿主状态。不要因已有输出文件就标记完成，或直接删除仍活跃的运行。

操作区别见 [Studio 使用指南](usage.md#6-studio查看定制和检验套件)。预览交互与试运行的“演示保存”不写当前设计项目；耐久保存需在普通项目中验证。

### 修改了 Bundle，Studio 仍显示旧内容

核对修改的是作者目录、Studio 内容库中的当前对象、独立副本，还是项目内 `design_kit` 文件，再核对当前显示的身份与内容来源。另一个独立 Bundle 副本不会自动换入 Kit 的挂载；源码 checkout 更新也不会替换已安装包。

复用已有组件的面板声明修改属于内容更新，按对应版本已有的重载或重新打开入口检查，不需要因此重编译整个宿主。新增共享组件则需要相应运行时发行。内容库原地保存后供未来项目使用；已有项目读取自己的 `design_kit`，需要更新时请 Agent 对比文件、保留定制并正常校验，不增加采用或版本发布步骤。具体边界见[内容维护](extending.md#结合-studio-维护内容)与[项目内容维护](kit-sharing.md)。

## 导入 Kit 或 Bundle 失败

当前源码的导入入口接收源码 ZIP、文件夹或单个 `SKILL.md`；Bundle 需方法文件，Kit 需 `mindset.md` 与 `kit.yaml`。导入产生独立身份，保留原文件；缺少其他辅助定义时仍可进入编辑器，按诊断补全。来源与许可证不是导入必填项，文件中已有的许可与署名仍应保留。安装版支持哪些入口需核对版本，具体步骤见[分享指南](kit-sharing.md#通过-studio-内容归档分享)。

路径、文件完整性或大小限制等错误仍需按具体诊断处理。当前导入入口最多接收 4096 个文件；Companion 请求的 12 MiB 限制包括 JSON 包装和编码，过大时会拒绝，不会截断材料。保留完整源码，选择已支持的完整目录接入或由作者整理交付，不删方法和必要资源来强行缩小。定义不完整可在编辑器继续保存和补全，加载、预览或执行时会报告实际缺项。导入不执行脚本、授予 Provider 信任或改变已有项目；接收源码不等于运行验证通过。

## 页面预览或资源无法显示

检查 artifact 是否已经保存、引用路径是否指向所属 Bundle，以及当前版本是否支持相关资源。Style/Page 预览目前支持 HTML 相对 `img src` 中的 PNG/JPEG/WebP；CSS 背景、字体和 `picture` 集合尚未按这条路径验证。

材料含 PDF、视频或外部页面时，读取取决于宿主能力；需要转换就明确转换，不自动安装解析器或放宽 CSP。面板能展示不代表所有按钮或原型导航已验证，按[演示与验证范围](preview-status.md)核对。

## 反馈时保留什么

记录插件/宿主版本、OS/架构、最小合成输入、操作次序、预期与实际结果，以及定位到的错误阶段。可以附去除私密信息的截图和错误片段。性能问题补充开始/完成时间及任务规模，避免仅描述“很慢”。具体渠道见[问题反馈](support.md)。
