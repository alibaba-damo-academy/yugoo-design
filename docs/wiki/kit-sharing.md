# 设计套件（Kit）的复制、版本选择与恢复

本页用于分享和接收语构设计系统（Yugoo Design）的设计套件（Kit）。可直接复制
[社区工作坊示例](../../examples/community-workshop-delivery/README.md)，
创作规则见[扩展开发](extending.md)。Kit 内容与 Design Project 是两类材料：
分享 Kit 不包含用户项目、会话、模型凭据或宿主安装。

选择与目标安装版相符的交付方式：Studio 归档通过其显式导入入口处理，完整内容目录通过宿主 loader 接入，npm 包由发行与宿主登记路径安装。三者不能只更换文件后缀互相替代。首次接收先在独立项目验证，避免覆盖正在使用的内容。

## Official Kits

官方设计套件（Official Kits）的用途、交付状态与实际接入范围如下。

选择前可先读[官方 Kit 用户指南](official-kits.md)，了解各类面板帮助你判断什么，以及如何开始一个小场景。本节继续集中维护版本、获取方式与接入范围。

**先安装主插件，再选择套件。** Web App 是默认随主插件交付的官方设计套件，
无需用户另行安装它的内部 npm 模块。Companion 在 payload 中携带完整 Web App
内容；DSH 整套发行通过依赖和包入口加载它。随装是内容可用，不代表自动为所有
项目选择套件；首次使用通过当前宿主的 `yugoo` 入口创建项目并选择 `web_app`，
已有项目继续保留原固定版本引用。主插件获取步骤见[安装指南](getting-started.md)。

| 官方套件 | 用途与方法 | 获取与适用范围 |
| --- | --- | --- |
| Web App（`web_app`） | 软件应用的需求、流程、规则、数据、页面、AI 能力及交接；见[方法与内容](../../packages/skills-web-app/README.md) | 默认随主插件交付。独立内容包的[精确 npm 元数据](https://registry.npmjs.org/@yugoo-design/dsh-design-skills-web-app/0.1.0-beta.2)提供 `dist.tarball` 下载地址；不需要为了首次使用再安装一次。 |
| 决策与运筹建模（Decision Modeling，`decision_modeling`） | 决策问题、对象、数据、约束、目标、模型、结果与比较；见[内部方法示例](official-kits.md#决策与运筹建模把业务经验带进模型内部验证) | 暂仅内部验证，不随默认产品交付，也不从公开源码导出；当前不推荐对外安装既有 npm 包。内部源码及将来独立安装的能力保留，尚不作为已交付的可选套件。 |

**2026-10-17（UTC）Web App 公开取包检查：** 其 npm 版本为
`0.1.0-beta.2`，精确元数据及完整下载的归档摘要已核对。
npm 发行版本不替代 Kit/Bundle 的内容版本。主插件及 DSH 整套依赖的公开可取性、
各宿主的加载/启用/保存重开与真实 Agent 使用，仍须分别检查[预览状态](preview-status.md)
和[宿主范围](hosts.md)，不能从内容包可下载推断主插件安装闭包完整。
游戏设计等仍是扩展方向，不列作已交付套件；下方社区示例也不冒充官方发行。

### 让当前 Agent 安装并选择默认套件

复制下面的请求给当前宿主的 Agent，并一并提供[通用安装提示词](../../packages/companion/HOSTS.md#default-prompt-any-supported-host)：

```text
请按通用安装提示词，为当前宿主安装语构设计系统（Yugoo Design），
保留现有模型、凭据、插件和项目配置。获取并核对精确发行版本；
Web App 应随主插件提供，不让我逐个安装内部模块。
完成宿主要求的启用或新会话后，检查实际可用套件中的 web_app。
为我创建一个新的设计项目并选择它，说明实际加载的 Kit 版本。
人工导入、授权或启用确有需要时再给出具体步骤；安装失败时报告具体缺项。
```

### 让当前 Agent 接入已交付的独立套件

安装包、已安装内容、被宿主发现和被项目选择是不同结果。以下请求适用于你已从作者
取得的完整独立 Kit，不是获取内部验证中 Decision Modeling Kit 的入口。
不要把 `npm install` 成功当作自动注册，也不要修改已有项目 pin 来试用新套件：

```text
我已取得作者交付的独立 Kit，想在新项目中试用。
请读取交付的 README，核对 Kit 身份、精确版本、来源、许可、
完整 Bundle 依赖和宿主兼容；若以 npm 交付，同时核对作者提供的精确包入口。
先查看当前安装实际提供的套件；若已有相同精确内容，使用它创建新项目。
按当前宿主已支持的完整内容包加载或显式导入入口准备，说明目标目录及必要授权；
没有可用接入路径时先报告缺项，不编造安装或更新命令，也不另建市场。
不要覆盖已有套件、项目固定版本或自动安装外部执行依赖。
接入后核对实际 Kit 身份/版本，使用一个新项目验证非空面板、保存与重开，
分别说明取包、加载、保存和原生 Agent 使用的验证结果。
```

完整内容包的目录接入见[DSH 发现与版本选择](#dsh发现冲突与显式版本切换)和
[Companion 显式入口](#companion显式目录与升级限制)；Studio 内容归档另走下面的导入流程。
Kit 内容可以独立发行，但当前没有已验收的通用“独立 Kit 一键更新”命令。
新版本发布不自动更换正在使用的项目：更新前保留完整原件、精确依赖与项目备份，
按宿主支持的显式迁移路径处理，或另建项目试用；不能只替换 npm 版本或项目 pin。

## 通过 Studio 内容归档分享

提供内容归档能力的 Studio 在工作区工具栏中显示“内容归档”。本节对应当前共享 UI 与 Companion 接线；各宿主安装候选的实际可用范围见[兼容说明](hosts.md)。

作者导出已安装 Kit：

1. 打开所需 Kit 的精确版本工作区，再进入“内容归档”。
2. 填写真实来源与许可证，选择“下载已安装 Kit 归档”。导出材料保留方法、文件及精确 Bundle 依赖。
3. 同时交付简短 README：适用任务、宿主/插件版本、可选或必需的外部环境、一个合成请求，以及实际验证范围。许可和原署名按下方要求保留。

当前 UI 下载入口针对已安装 Kit，不能把本地未发布副本当成已经导出的新版本。分享副本前使用目标版本实际支持的交付入口，或整理完整目录和依赖；原始目录 ZIP 不是 Studio 归档 JSON。

接收者准备并采用：

1. 在“内容归档”选择归档文件或粘贴完整 JSON，点击“准备导入”。
2. 查看身份、精确版本、保留文件、来源、许可证和定义诊断；校验失败先交作者修正。
3. 明确选择“采用 Kit 并创建工作副本”或“采用 Bundle”。Kit 采用会保留精确内容并打开新建的未确认副本；独立 Bundle 采用后打开其源码工作区，仍需明确挂载到 Kit。
4. 在支持采用内容选择的 Companion 版本中，创建独立设计项目，核对命令返回的可用 Kit 列表，再通过 `kit <kit>` 选择已采用的套件。命令、MCP 和 Panel 必须使用同一个内容库状态（`--state-root`）；已有项目继续保留原 pin。完成下面的[接收者验证](#作者与接收者的最小验证)。作者另行交付完整内容包时，也可使用[显式目录入口](#companion显式目录与升级限制)，它是另一条加载路径。实际安装版须包含该选择能力，验证范围见[采用后选择](#采用后选择的验证范围)。

准备导入只保留归档与校验结果，采用也不会执行脚本、安装模型/Provider、发布新版本或更改既有项目 pin。相同 pin 的相同内容可以复用，不同内容会被拒绝。来源与许可证字段是声明，不代替作者身份和分发权限核查。协议与资源边界见[归档契约](../../packages/studio/docs/content-archive.md)。

## 交付格式与依赖说明

交付应保留 **Kit 与它引用的精确 Bundle 内容**。当前文件布局将 `kits/` 与 `bundles/`
分开；可用内容包组织这些文件，由 `package.json.designSystem.kit` 声明入口。加载这种包时，
将包根目录交给支持包解析的入口；仅提供 Kit 目录还需显式配置精确 Bundle resolver。
不能只凭目录中存在 `mindset.md` 就认定依赖完整。结构见[扩展开发](extending.md#当前内容组织)。

ZIP 和 Git 可以运送完整文件；普通 ZIP 解压后仍需按包入口或目录入口加载，不能直接当作
loader 输入。Studio 内容归档有自己的格式及显式导入入口，以安装版本和
[归档契约](../../packages/studio/docs/content-archive.md)为准。不要只分享 Panel 或用户项目的 Design Files。

每份交付应包含或在 README 中列明：

- Kit 的稳定 `name`、`version`，各 Bundle 的身份和版本；保留对应 manifest、
  方法、schema、validation、Panel、摘要声明、语言资源和方法引用的文件。声明式摘要使用 `skill.yaml.summary`。
- 自有 LICENSE/NOTICE 及复制内容必要的原署名、第三方材料。压缩和 Git 分享
  不改变原许可；不要把运行时组件的许可归到 Kit 自有代码名下。
- 兼容要求：实际使用的宿主/插件版本，以及必需的声明式组件、资源协议或
  native Provider。只有实际验证过的版本可以称为已支持；未知版本先验证，
  不因 loader 能读 manifest 就声称所有交互兼容。
- 脚本与外部依赖：列出方法会调用的脚本、运行环境及外部包/服务；说明它们
  是随目录交付还是需独立安装。目录 loader 不执行安装脚本，也不会自动解析
  npm 依赖或下载外部 Kit。缺少依赖时停在具体缺项，不让 Agent 临时编造实现。
- 可恢复原件与更新说明：分享精确目录版本，并可附文件摘要；明确是否涉及
  schema/语义变化。项目 checkpoint 和版本号都不能代替完整 Kit 内容备份。

社区工作坊示例是无需外部服务或求解器的内容 Kit，复用已安装的通用 Panel
组件；其目录/ZIP 使用结果见下方适用边界。带 native Provider、额外脚本环境
或外部包的 Kit 必须另外给出对应依赖的安装入口，不能沿用这个无额外依赖
示例的结果宣称解压即可运行。

### npm 内容包的选择

正式分发以 **npm 承载插件和可独立更新的内容包**，GitHub 承载公开源码；
目录/ZIP 是已有示例验证过的内容形状和补充分享方式，不能替代 npm 发行目标。
不要求因此拆仓库或建设 Kit 市场。

现有 Kit loader 没有通用 npm 安装、依赖解析或自动注册入口；`npm install`
成功并不意味着 Kit 已被选择。发行接入仍须约定包内 Kit 根目录、身份/版本
与许可证保留，并由宿主明确把已安装目录接入 loader。带运行时代码的包
仍需独立满足宿主注册、依赖及安全要求。npm 命名空间为 `@yugoo-design`，
预发布渠道为 `beta`；当前包的发布状态见[预览状态](preview-status.md)。
npm 发行版本不改变 Kit/Bundle 的内容版本。实际发布仍需核对账号权限，
并按独立发布流程执行；不能从 Companion 已发布推断所有独立内容包都已发布。
上方官方清单记录当前对外提供的内容包及内部验证状态；其他 Kit 的包发布与宿主接入须按各自实际结果说明。本节的目录分享步骤不证明独立包已经发布，也不代替完整安装验收。

## 先保存可恢复的原件

1. 保存完整内容包或等价的精确内容集合：Kit 的 `mindset.md`、`kit.yaml`、可选关系声明，
   以及各独立 Bundle 的方法与资源、LICENSE 和 NOTICE。记录 Mindset、Kit 与 Bundle 的身份和版本。
   旧示例的 `skills/` 布局仅按其兼容 loader 使用，不作为新内容的目录规范。
2. 将未修改的原件或完整 ZIP 保存在发现目录之外。给副本使用不同目录名，
   不覆盖收件方已有 Kit；目录名本身不改变 Kit 身份。
3. 普通 ZIP 应包含完整内容与入口说明。收件方先解压，再按目标宿主支持的包解析或目录
   加载入口接入；裸 Kit 目录还需能解析其精确 Bundle 引用。不要把运输 ZIP 当作 Studio 归档。
4. 首次使用创建新项目，核对实际显示的 Kit 名称和版本，再生成、编辑和保存。
   不把未知版本的 Kit 直接放到已有项目正在使用的路径上。

项目记录精确的 Kit 引用，并可能记录成员 Bundle 版本及完整内容摘要
（`contentHash`）。**固定版本引用（pin）不代替完整原件备份**：带有内容摘要的
引用会检查实际内容，变更后的同名同版本定义不能自动作为原件使用。旧项目可能
没有摘要字段，也不能据此保证同版本替换安全。保留完整方法、Panel 与资源；
项目 Git checkpoint 保存项目数据，不代替外部 Kit 目录备份。

## 独立定制：复制新身份

如果要长期维护自己的领域方法，复制成独立 Kit 比覆盖原件更清晰：

1. 在发现目录外准备副本，修改 `mindset.md` frontmatter 的 `name` 为新的
   稳定 id，并同步面向用户的名称、说明、方法与例子。
2. 核对 Bundle manifest、资源及身份引用；有 `relations.yaml` 时同步其中
   当前 Kit 的命名空间和领域引用。不要盲目批量替换用户数据或 canonical 字段。
3. 保留来源署名和许可材料。只复制 Kit 时继续引用原来的精确 Bundle，不获得它们的私有副本。
   要修改某个 Bundle，先建立新的独立目录身份（catalog identity），再修改副本并更新 `kit.yaml`
   的精确挂载。保留运行时 `name`、方法约定与 canonical 数据路径，避免破坏既有数据；
   新身份不继承 native Provider 信任，同一 Kit 的运行时绑定不得重复。
4. 使用文件来源时，新 Bundle 目录与 `skill.yaml.identity` 对应独立身份，`kit.yaml` 挂载项的
   `name` 指向它；运行时 `skill.yaml.name` 与挂载 `bindingKey` 保持原有约定。
   `<design_skills>` 是挂载清单的模型侧投影，须随挂载保持一致，不另立第二份成员权威。
5. 加载副本，确认看到新身份，为它创建新项目并显式选择。旧项目仍用原 Kit。

同一精确 Bundle pin 对应不同内容会被拒绝；不能通过换 Kit 名绕过这个限制。
改文件夹名本身不会产生新内容身份。DSH 已加载的来源不允许在进程中直接改 Kit `name`；
应先在新目录完成副本，避免改动运行中的原来源。

## DSH：发现、冲突与显式版本切换

安装版默认发现根为 `$DSH_HOME/design-system/kits`；未设置 DSH_HOME 时为
`~/.dsh/design-system/kits`。把 Kit 放到该根的一个直接子目录；额外根使用
loader 的 `discoveryRoots` 配置。不会递归扫描所有工作区，也不会执行 Kit 脚本。
先确认当前安装版本包含该发现能力；源码修改不会更新旧安装。

在新版 DSH 当前会话中，新项目的操作入口为（旧安装候选按随包指南）：

```text
/yugoo new workshop-copy
/yugoo kit community_workshop_delivery
```

也可通过实际宿主的 Design 选择界面或 Agent 选择；以显示的 Kit 名称和版本为准。

**两个目录同名时**，不会按版本号自动合并。显式来源先加载；默认发现根优先于
额外根，额外根按配置顺序、根内按目录名顺序处理。同名异源会诊断并保留已注册
来源，即使两个目录声明不同版本。处理步骤是：保留两份备份，将不使用的同名
目录移出发现根，或把独立定制副本改为新身份，然后正常重启宿主并确认目录。
不要依赖目录排序来选择升级版本。

**新项目首次选择套件时**，从已安装且完整验证通过的套件组合中选择可用版本。
目录中出现新内容不会自动修改已有项目的固定引用；已有项目继续解析它记录的
完整精确版本。无法解析原版本时，应恢复原件，不能自动改用新版。

对已选择套件的项目，再次执行 `/yugoo kit community_workshop_delivery`
会保留原有精确 pin，不会升级到当前新版；选择不同 Kit 身份也会要求显式语义迁移。
若原 pin 不可解析，先恢复完整原件。该选择命令不支持通过
`name@version` 任意切换旧版本，也不是迁移命令。

升级或更换 Kit 需要用户明确目标，并使用安装宿主实际提供的显式迁移流程。
先保存面板编辑，备份项目与完整源、目标套件，再按领域方法验证已有事实、
设计文件、相关产物和跨 Bundle 引用，核对保存与重开。可以另建项目试用新套件，
但新项目可用不等于旧项目已迁移。不能只改项目 pin 或版本字符串来完成升级。

## Companion：显式目录与升级限制

Codex、Claude Code、Qoder CLI 的 Companion 使用已安装插件的实际入口，
通过 `--kit /absolute/content-entry` 指定安装版支持的内容入口。结构化内容包使用包根目录；
裸 Kit 目录必须能解析所挂载的精确 Bundle，不能只移动 `mindset.md` 后期待自动寻找依赖。
项目命令、MCP 和 Panel 服务必须指向同一目录及同一项目管理状态；沿用该宿主
已有的 session/thread 绑定和启动指引，见[Companion 文档](../../packages/companion/README.md)。
不要照搬 DSH 的发现根来期待 Companion 自动发现，或虚构通用安装命令。

### 使用完整内容包创建新项目

以下 Bash 示例使用目标 npm 安装内的项目运行入口。先确认该安装包含
`payload/shared/scripts/design.mjs`，并按[内容包入口](extending.md#当前内容组织)
交付完整 Kit 与 Bundle。`design-system` 是安装器命令，不代替这里的项目命令。
由当前 Codex Agent 填入真实安装目录、完整内容包根目录及当前会话 ID；
状态和项目目录使用单独的新目录，不借用已有项目的配置：

```bash
YUGOO_RUNTIME="/absolute/npm-install/node_modules/@yugoo-design/companion"
YUGOO_KIT="/absolute/my-content-package"
YUGOO_STATE="/absolute/new-companion-state"
YUGOO_PROJECTS="/absolute/new-design-projects"
YUGOO_THREAD="当前 Codex 会话的真实 ID"
yugoo_args=(--kit "$YUGOO_KIT" --state-root "$YUGOO_STATE"
  --projects-root "$YUGOO_PROJECTS" --host codex --thread "$YUGOO_THREAD")
node "$YUGOO_RUNTIME/payload/shared/scripts/design.mjs" command \
  --input "new Workshop" "${yugoo_args[@]}"
node "$YUGOO_RUNTIME/payload/shared/scripts/design.mjs" command \
  --input "kit my_kit" "${yugoo_args[@]}"
```

`my_kit` 必须与交付包的 Mindset `name` 一致。核对返回的可用 Kit、项目根目录
和已记录的精确 pin，然后按目标宿主指南让 MCP 与 Panel 服务使用同一个 `--kit`、
项目管理状态和真实会话绑定，并连接到新服务。Claude Code、Qoder CLI 使用各自
的 `--host` 值和原生会话参数，不沿用示例里的 Codex 会话。

此步骤使用的是作者交付的完整包。Studio 保留库将 Kit 与各 Bundle 按身份和
版本分别保存；不能把单个保留 Kit 的 `sourceRoot` 当成完整包根目录传给 `--kit`。
当前该路径不能自动找到分开保存的 Bundle。保留内容通过同一个状态目录中的
内容库解析完整精确依赖，不需要将保留文件拼成另一份包。完整目录包加载有源码/API
隔离验证；归档采用后的异名选择另有下方记录的安装包与原生 Agent 验证。
两种入口的证据分别记录，不能互相替代或外推到所有宿主。

Companion 的 `kit <kit>` 选择当前服务暴露的套件。已有项目重选同名套件时
保留原 pin，并通过内容库解析对应精确版本；更换 Kit 身份或无法解析原 pin 时
会拒绝，不会隐式升级。迁移入口与支持范围按安装宿主版本核对，不把源码中的
迁移能力视为所有宿主都已完成验收。另建项目试用新套件时，使用实际新目录和
对应服务连接，保留原项目与原 Kit；不要将仍绑定旧目录的连接文件当作新连接。

## 缺失版本与恢复原内容

若已有项目显示待恢复、固定版本不可用或不可写：

1. 记录项目显示的精确 Kit 名称和版本，暂停生成与 Panel 保存。保留项目文件、
   Git 历史及原 Kit 备份，不手改 `project.json` 的 pin 来消除提示。
2. 从作者或自己的备份恢复该名称和版本的完整 Kit。仅修改新版的版本字符串
   不能恢复旧内容，也不能证明兼容。
3. DSH：恢复合法原来源目录并等待加载；需要重新选择来源或身份时正常重启。
   Companion：正常结束服务，用恢复的原 Kit 目录重新启动，保持原项目和实际
   会话绑定。目录不存在时先恢复目录，不能假设服务能提供只读回退界面。
4. 确认项目 pin 与加载 Kit 一致、访问恢复可写，再打开原 Bundle，检查实际
   字段和既有记录。之后按方法继续工作。

恢复能力取决于安装宿主是否保留了完整的已发布内容，以及该内容能否解析为
项目的精确引用。仅有进程级 last-good 不能代替完整备份；也不能一概认为
工作目录变化就会使保留版本失效。若固定版本仍无法解析，必须恢复精确原件；
重选当前版本不能绕过该要求。需要升级时另走显式迁移流程。

如果只是要撤销 Kit 的 Panel、文案或方法改动，先保存项目编辑，再恢复备份
中的完整 Kit 内容，并确认它能解析为项目记录的精确版本与内容摘要。不要将
“同名同版本”视为内容相同；被拒绝时按具体诊断恢复原件。
恢复 Kit 不会自动撤销已保存的项目数据；
项目内容修订仍走对应 Bundle 的受控校验和 checkpoint 路径。

`migrate` 项目命令在保留原件的前提下，将已有设计项目的 Design Files 迁移到新项目并校验、适配；它不负责下载或找回缺失 Kit，也不原样复制完整历史。项目参数见[命令参考](commands.md)，设计文件与运行状态的保留范围见[项目文件管理](project-files.md)。
Git 仓库、市场安装、依赖 Kit 自动解析和跨机器迁移都不是本页步骤隐含的能力。

## 已验证与适用边界

### 采用后选择的验证范围

**2026-10-14 验证范围：** 独立作者按公开指南创建的小型声明式 Kit/Bundle，
已在安装版 Companion `0.1.0-beta.2` 中完成 Studio 归档上传、
准备与显式采用。接收者的新 CLI 进程能发现并选择异名 Kit，读取字节一致的
保留方法与资源，并按精确 pin 重开项目；不依赖作者的源码工作区或完整仓库副本。
采用仍不授予执行信任；缺少对应可信运行时贡献的套件会被拒绝。

归档 UI 使用与已发布制品一致的本地发行归档安装；后续原生阶段则使用从
npm registry 安装的同版 Companion。在独立测试项目中，Codex 原生 Agent
按该 Kit 的方法从合成需求生成结果；
浏览器将库存从 8 改为 10 并保存更正备注，同一原生会话收到保存通知。
后续正式发布将需求 12 的缺口从 4 更新为 2，并保留用户输入、记录身份、
排序及另一条记录的未知库存。独立复核确认刷新与关闭后重开均显示已提交的新结果。
此前源码/API 的错误输入拒绝及相同请求重试复用同一提交也保留为单独验证。

本次首次续作因测试会话禁止审批而被拒绝；用户授权后，以正常审批模式显式
重试才完成发布。因此已验证自动通知消费与授权后的续作，不宣称全程无需人工
确认、后台评审完成或所有宿主通过。该例不含 native Provider、求解器或其他
执行依赖，也不证明从未安装状态的一键安装；作者/接收者仍按下方要求验证自己的交付。

### 作者与接收者的最小验证

一个可分享的 Kit 不只要能加载。作者和独立接收者分别记录插件候选、Kit/Bundle 精确版本、合成材料与实际结果：

| 检查 | 作者 | 独立接收者 |
| --- | --- | --- |
| 资源完整 | 从运行期入口读到完整方法、契约和引用资源 | 仅凭交付材料和公开指南完成读取 |
| 装载与校验 | 非空合法样例通过，错误输入被拒绝 | 在干净的独立配置中加载对应内容 |
| 原生设计 | 生成一个有价值的设计结果 | 不依赖作者原会话或私有文件生成结果 |
| 交互与续作 | 编辑、正常保存、重开并让 Agent 基于修改继续 | 独立重复相同闭环 |
| 外部执行 | 按需实际运行并保留输入、结果和限制 | 核实依赖可取得；未运行的能力明确记录 |

运筹建模 Kit 若声称可求解，还须实际求解、解释结果，修改约束或参数后重算。仅生成模型、读取 manifest、预览面板或导入样例不能证明求解完成。接收者不能依赖作者机器上的私有绝对路径、源码工作区或未交付依赖。

这些是交付验证要求。上方的小型声明式 Kit 分享验收不代替运筹 Kit 的真实案例、
求解与修改后重算验收，也不替代其他含执行依赖的扩展测试。首发不承诺所有历史内容
格式自动迁移；`migrate` 保留已有设计项目原件，并在新项目中按当前契约校验、适配，
与恢复缺失的精确 Kit 原件分别处理。
