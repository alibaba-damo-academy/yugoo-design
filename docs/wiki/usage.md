# 使用指南

在熟悉的智能体宿主（Agent Host）中提出目标，通过设计面板（Design Panel）查看和修改结果，再让 AI 基于已保存的设计继续。先完成[开始使用](getting-started.md)，各宿主入口见[兼容说明](hosts.md)。本页先介绍设计项目中的日常协作，再介绍设计工作室（Studio）的内容创作。

## 1. 选择项目与目标

DSH 可使用 `/yugoo new <name>`、`/yugoo open <id|name|path>` 和 `/yugoo status`；Companion 使用已安装的 `yugoo` 技能与项目操作入口。项目文件独立于聊天，可从其他会话继续打开。

统一项目入口为 `yugoo`，不注册 `design` 命令、入口技能或兼容别名；具体前缀遵循宿主原生语法。已安装版本是否包含这一修正，需按实际包版本核对，源码更新不会自动替换宿主插件。

例如，在 DSH 新建项目可使用 `/yugoo new research-platform`；需要手动选择 Web App Kit 时，可使用 `/yugoo kit web_app`。本页命令对应当前源码，`mindset` 保留为 `kit` 的旧别名；旧安装版按随包帮助核对入口。其他宿主的指令形式按[宿主指南](hosts.md)查看。

描述需要的结果，例如：

```text
请梳理工作室项目交付平台的功能模块，并说明重要例外。
请调研同类产品并保留引用
请生成核心业务流程
请根据现有设计生成高保真页面原型
请把当前设计整合成一份 PRD
```

主 Agent 结合设计套件（Kit）的领域主提示词（Mindset）、当前目标和已有证据选择方法。已有明确目标时可以直接请求相应结果；还不清楚从哪里开始时，可以请它提出适合当前情况的设计活动，并说明各自能解决什么问题。无需先完成全部访谈或按清单运行所有设计技能包（Bundle）。

开始时不必准备完整需求。可以先说明实际情况、在意的结果和这轮边界，例如：

```text
我们用聊天沟通客户修改，经常说着说着就增加了交付内容。
先给我一个能讨论的修改处理流程，解释有哪些选择。
设计师可以整理意见，新增范围和交期由项目负责人确认。
这轮先不做合同收费和财务管理。
```

你提供业务背景和取舍，AI 用当前 Kit 的专业方法帮助展开。遇到无法回答的问题，可以要求先看一个例子、解释影响或采用可修改的暂定方案；尚未确认的信息应保留为未知或假设。

## 2. 查看并修改 Panel

在当前设计的 Panel 中查看结构、图表和 artifacts，修改可编辑字段并保存。Panel 和图中的详情表单操作同一份数据；实际控件与编辑能力由安装版的 Bundle/Panel 声明决定。

保存后重新打开，核对修改已保留，再请求下一步设计。校验错误、并发冲突或未完成的后续处理需要按界面诊断处理，不把一次点击当作保存成功。

例如，AI 展开功能模块面板后，你可以删掉第一版不需要的功能、修改优先级，再要求“根据已保存的范围，展开客户修改请求的流程”。在流程面板中继续讨论谁记录反馈、谁确认范围和交期。这个过程把讨论落实为可继续修改的成果，而不是每一轮都从聊天描述重新猜测。

反馈可以落在具体对象和实际影响上：

```text
这里把每项修改都交给负责人。我希望设计师能直接处理范围内的布局调整，
新增页面或业务能力才讨论范围。请调整这个分支，并检查已有规则是否需要修订。
```

面板中的直接修改适合表达确定的字段和关系；需要解释原因、比较方案或联动其他设计时，可以结合对话提出。希望 AI 看到的面板修改应先保存，再指明需要继续推敲的地方。

面板保存和原生 Agent 续作分别确认：看到保存成功后，检查宿主是否已消费本次修改；需要进一步推敲时回到原会话提出具体请求。等待输入、排队、执行中和完成是不同状态，消息发送状态不明时先检查原会话，不反复提交。

## 3. 处理建议

Grounding、Reflection、Alignment 可以提出疑点、研究或澄清建议。查看、接受、拒绝或稍后处理按实际宿主入口执行。建议本身不修改设计文件，接受后仍通过正常 Bundle 路径修订。

例如，允许设计师直接处理范围内修改后，审查可以提示你考虑这些修改对已承诺交期的影响。先看建议引用了哪些设计，再判断是修订、解释现有规则，还是暂不处理；不要仅凭建议文字把它当成已确认的新要求。完整情境见[工作室协作教程](web-app-demo.md#4-用一条建议发现尚未想清楚的取舍)，审查视角和能力边界见[知识关联与审查](concepts.md#知识关联与审查)。

支持自主审查的安装版允许通过审查设置选择是否后台检查。关闭自主审查后仍可主动请求检查；具体入口和后台能力以[宿主兼容](hosts.md)为准。

后台不可用，或原生异步评审仍占用主对话时，本轮共享源码已实现的通用方案是先询问“关闭自动 GRA”或“本次在主对话同步评审”。同步方式会占用对话，须经用户确认；未选择时不改策略、不运行评审，关闭自动 GRA 后仍保留手动请求。已检查的千问办公 `1.3.2` 限制与该方案的实际交付状态见[后台能力与评审降级](hosts.md#后台能力与评审降级)。

### 决定下一步做什么

有用的下一步建议会说明：当前还缺什么、为什么会影响你的目标、这次行动能帮你看清什么。它可以是展开另一个面板、补充研究、比较方案，或返回已有设计修订。GRA 的一项发现可成为讨论依据；是否采用、如何落实，仍需结合当前请求判断。

如果宿主显示清晰度评估（U/S/T），结合理由和所对应的设计版本阅读。新增背景可能让分数下降，未使用的 Bundle 也不自动成为剩余工作。保存成功或审查完成，分别不等于已有最新评估；显示缺失、失败或旧版本时，不据旧分决定下一步，见[评估排查](troubleshooting.md#清晰度或下一步建议没有更新)。

你可以明确说“先修改这一点”“这个问题以后再看”“先给我草案”或“当前范围已经足够”。当设计已满足这轮用途，可以总结决定、保留未决事项并交接；应用设计可整理为 PRD，其他领域按自己的产物形式交付。

## 4. 管理与恢复

设计项目（Design Project）独立于聊天。DSH 的常用入口如下；Companion 使用其已安装 Skill 或共享项目工具执行同样的项目操作，不照搬 DSH 前缀。

| 想做什么 | DSH 当前入口 | 结果 |
| --- | --- | --- |
| 查看当前项目和套件 | `/yugoo status` | 检查当前会话选择 |
| 查看项目列表 | `/yugoo list` | 找到已有项目 |
| 选择设计套件 | `/yugoo kit <kit>` | 为当前项目选择 Kit；不隐式升级已有精确版本 |
| 打开已有项目 | `/yugoo open <id\|name\|path>` | 将项目绑定到当前会话 |
| 关闭当前绑定 | `/yugoo close` | 保留项目文件，结束当前会话的选择 |
| 适配既有设计材料 | `/yugoo recover <path>` | 保留原件，在新项目中验证和适配 |
| 从文档、截图或源码还原 | `/yugoo reconstruct <path>` | 原材料只读，结果进入新设计项目 |

新建项目默认位于当前操作系统 Documents 下的 `YuGoo/Projects`；显式配置的路径优先，已有项目不会自动搬迁。WSL 使用 Linux 用户目录，不自动转向 Windows 的 Documents。项目 Git checkpoint 记录设计变更，关闭会话不删除这些记录。

项目操作中的 `delete` 移除注册记录，保留实际项目文件；不要把它当作文件删除或清空目录。精确内容版本无法解析时，按[原件恢复](kit-sharing.md#缺失版本与恢复原内容)处理，不手改项目 pin。项目命令的职责见[共享入口契约](../design-command-agent-entry.md)。

## 5. 从既有材料重建设计

以下保留已有 DSH 重建方法；其他宿主是否提供该入口以其版本指南为准。

重建材料须使用绝对路径，例如 `/yugoo reconstruct /data/product.md`
或 `/yugoo reconstruct /data/product-materials`。目录可混合文档、截图和代码，
不要求 Git；单文件输入仅针对该文件。材料保持只读，生成结果写入新设计项目。
材料能否被理解取决于宿主提供的读取能力；不支持的 PDF、视频等格式会提示转换，
不会自动安装解析器。截图不证明后台规则，文档中的计划不自动视为已实现功能。
既有设计项目材料的适配使用 `/yugoo recover`；它不是支持所有旧格式的版本迁移保证。

`recover` 不读取或重放旧 Session。它保留来源目录不变，将当前 Mindset 能识别的 Bundle 文件暂存到一个新的当前格式项目；Agent 随后使用各 Bundle 现有 validator，验证通过则直接发布，失败则按当前 Skill Body 与诊断做最小适配。

`reconstruct` 面向原始材料而不是旧 Design Files。它创建并打开一个空项目，然后由主 Agent 对指定材料做有边界的只读扫描，选择合适的设计套件（Kit）并加载其领域主提示词（Mindset），再判断哪些 Bundle 对还原产品设计真正相关。Agent 可以检查全部 Bundle 的说明，但不会机械运行全部 Bundle；选中的 Bundle 继续使用各自原有的 Schema、validator、文件写入与 Git 发布流程。不会整仓复制或建立额外源码索引；必要的原始图片可以原样复用到所属 Bundle 的 Design Files。

重建 Producer 执行的是事实抽取与产物转换，不是正向设计 Skill Body：把已有内容填入相同的可交互结构，保留真实界面和素材，而不是另选风格或另造页面。格式/脚本用法来自 Bundle 的共享产物参考。未知可使用现有字段表达；若材料不足以满足必填契约，会明确报告限制，不把默认值冒充事实。完成后这些仍是普通设计文件，可在面板保存修改并继续设计。

素材由主 Agent 使用现有宿主文件操作，在所属 Producer 启动前准备，并检查源/目标实际路径边界；不与 Producer 并发写入，不覆盖不同内容，也不经模型转抄 base64。Producer 使用现有图片字段引用，再走普通校验与发布。若宿主缺少可靠复制能力，应报告限制，不把重新绘制的 Logo 当作忠实还原。此流程没有新增素材工具或自动导入服务。

Style/Page 预览共用现有二进制文件接口，将 HTML 中相对 `img src` 引用的 PNG/JPEG/WebP 装配为沙箱可显示的图片，不改原 HTML 或放宽 CSP。图片更新、出现或删除沿用公共轮询的文件哈希刷新。它不是任意源站资源加载器：CSS 背景、字体与响应式 picture 集合不在这次支持范围内，相关还原限制需要说明。

重建先识别用户入口和实际行为，再组织功能、流程、页面等相关维度；跳过普通设计的中途 `must_edit` / `user_continue` 确认，完整产出后统一交给用户审阅。真实失败与输入障碍仍会报告，不会被当成完成。Agent 在结束前核对覆盖范围与跨 Bundle 矛盾，说明推断、未知和跳过的维度。

主 Agent 先在对话中整理精简的共同理解：产品边界、实际入口与操作、关键流程与数据、源码位置及未知项，再通过现有 `brief` 向每个相关 Bundle 传入其所需证据与已保存的引用 ID。后续发现会修正这份理解；不是先完整建图才能工作，也不会把所有源码搬进上下文。

Ladybug 可用时，主 Agent 可按实际需要通过 `design_reconstruction_knowledge` 记录或查询带源码路径、短引用和文件内容哈希的理解关系；包括未提交的源码改动。不会自动向每个 Producer 灌入整份图谱。图记录只是 AI 提出的理解，Producer 必须回查源码，文件变化会标为证据已变更。图不可用不会阻止重建，也不改变 Design Files 的事实地位。

重建收尾由主 Agent 按提示调用一次原生只读子代理，核对当前源码、实际设计文件、跨 Bundle 引用含义和产物可读性。审查输入提供材料、范围和开放问题，不预设“某项差异合理”等答案。源码能够证明的还原错误，经主 Agent 核验后交回对应 Bundle 修复；错误的共享定义先修正，再检查消费者，不能让页面迁就错误的视觉规范。未知事实和产品选择留给用户。它不是自动接受 GRA 建议，也不是新增的后台完成门禁。独立审查不可用时由主 Agent 自查并说明限制；这是 agentic 工作约定，不是运行时强制保证。收尾分别说明机械校验、源材料对照、未做的浏览器验证及尚存偏差，不将格式通过等同于忠实还原。

Web App 重建会把已有视觉语言还原为 Design Style，再生成对应的具体页面 HTML；宿主提供主题不等于可以跳过视觉证据，页面地图也不等于页面重建完成。Smart Questions 可承接源码支持的产品背景和未决意图，预填内容会区分事实、推断与未知，不冒充用户作答。完成前核对真实落盘文件、引用及覆盖情况，无法还原的部分明确报告原因。

## 6. Studio：查看、定制和检验套件

Studio 管理构思时使用的方法和面板，日常 Design Panel 编辑的是你的设计成果。Companion 可从设置打开 Studio，在独立浏览器页中沿用当前服务连接；DSH 使用宿主提供的 Studio 入口。不同安装候选提供的创作能力可能不同，先核对[宿主指南](hosts.md)。

### 查看套件与技能包

从左侧“套件”进入 Kit，阅读 Mindset 并查看已挂载的精确 Bundle 版本。“原始文件”提供实际文件树，可以查看完整 frontmatter、挂载投影和参考资源。阅读视图方便浏览，原始视图保留文件内容。

从“技能包”查找 Bundle，查看方法、输出契约、schema、validation、语言资源和面板声明；详情也显示哪些 Kit 引用了它。Kit 挂载 Bundle 并不会复制一份独立源文件。

### 复制后定制

支持本地副本的安装版可在 Kit 或 Bundle 页选择“复制”，在现有列表中打开标为“本地副本 · 未发布”的内容：

1. 打开副本的“原始文件”，编辑可编辑的文件并保存。
2. 切换文件或离开前处理未保存内容；刷新后显式选择原副本，检查已保存文本。
3. Kit 副本的“挂载管理”选择精确 Bundle 版本。只复制 Kit 时仍引用原 Bundle；要改某个 Bundle 的方法或面板，先创建其独立副本，再调整 Kit 挂载。
4. 用样例预览检查改动。要在设计项目中采用，先按[分享指南](kit-sharing.md)准备经过验证的完整可加载内容，再使用宿主已提供的接入和套件选择入口。保存副本不会发布新版本或切换当前项目 pin。

标题处的重命名修改展示名称，不改变 Kit/Bundle 的技术身份。删除本地副本会检查引用，并保留可恢复数据；它不是卸载已安装内容。Mindset 原页的正文编辑和 Panel YAML 草稿也保存在独立工作副本中，安装原件保留。

完整副本的发布、试运行和运行期采用需要各自的宿主接入；保存或样例预览不隐含这些能力。下面的原生试运行说明针对已经接入的已安装 Bundle 或已保存 Panel 草稿。

### 预览与试运行

| 操作 | 适合检查什么 | 保存与执行的含义 |
| --- | --- | --- |
| 面板预览 | 用 Bundle 样例检查布局、字段与声明 | 使用隔离样例，不启动模型，也不修改设计项目 |
| 编辑 Panel YAML 后预览 | 检查声明式 UI 改动及诊断 | 源码草稿保存与样例交互是两件事 |
| 原生试运行 | 检查方法能否生成结果，以及结果面板 | 连接检查通过后向宿主发起真实任务，使用独立测试项目 |
| 日常 Design Panel 保存 | 修改当前项目的设计成果 | 经过项目校验与版本记录，供后续构思使用 |

Bundle 的“面板预览”优先读取其 `reference/preview.json`；没有可用样例时会显示诊断，不能把空界面当成完整体验。声明式面板可以编辑 YAML；native 面板由 Provider 实现，不提供可编辑的 `panel.yaml`。

试运行从 Bundle 标题处发起。已有 YAML 改动应先保存，再运行对应的确切草稿版本。首次可由原生 Agent 准备具体合成输入并执行；你也可以修改测试输入后明确重新运行，每次保留独立结果和原始输入。排队或连接可达不代表任务完成，未知执行状态不应当成成功，也不应重复启动。

试运行面板中的“演示保存”和“撤销修改”只演示当前浏览器的已保存界面状态，不发布设计文件或通知 Agent 继续；刷新会恢复真实生成结果。要验证耐久保存和续作，仍需在正常设计项目中完成操作。

### 组件与分享

支持“面板组件库”的安装版可查询同版本的声明式组件，查看合成示例并复制完整声明。组件库用于选型和学习；新组件仍需共享运行时注册与发行，不能在此安装任意可执行 UI。

Studio 也可作为内容维护时的可视化工作台：查看真实样例、操作面板、指出表达或交互问题，再修改并重新查看。完整 Bundle 的方法、数据契约和组件协同维护仍需结合作者源与开发 Agent；已有 YAML 编辑或原生试运行入口不代表 Studio 已具备完整的对话式创作能力。作者流程见[扩展开发](extending.md#结合-studio-维护内容)。

“内容归档”支持导出、准备导入和明确采用 Kit/Bundle。准备导入只保存材料和校验结果；采用 Kit 会保留精确内容并创建未确认工作副本，独立 Bundle 则进入内容库，仍需明确挂载。具体步骤、来源与依赖要求见[分享指南](kit-sharing.md#通过-studio-内容归档分享)。

以上操作按当前共享 UI 与 Companion 接线说明，不意味着所有宿主候选已通过每项交互验收。服务和作者职责分别见 [Studio domain](../../packages/studio/README.md) 与 [Studio UI](../../packages/studio-ui/README.md)。设计成果交给后续实现时，使用[设计到开发交接](../design-development-handoff.md)。
