# 从设计项目开始一项开发任务

本指南说明如何让一个没有原设计对话的新 Coding Agent 使用设计项目。
接收方读取已有设计文件、检查点和 KAG，先整理开发规格，再在用户授权的
范围内实现。它沿用开发项目的需求格式，不自动生成完整应用。

## Spec 文件模式：先兼容已有实践

开发交接应增强开发项目现有的 spec，而不是另创 Yugoo 专用需求格式。
截至 2026-10-04 的调研，以下是有实际采用证据的主要组织方式；它们是不同
工具的约定，不是一个统一、强制的行业文件标准。

| 实践 | 现有文件组织 | 区分的职责 |
| --- | --- | --- |
| [GitHub Spec Kit](https://github.com/github/spec-kit/blob/main/templates/plan-template.md) | `specs/<feature>/spec.md`、`plan.md`、`tasks.md` | 用户需求与验收、实现方案、可执行任务 |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/overview.md) | `openspec/specs/<domain>/spec.md`；`openspec/changes/<change>/` 下 proposal、spec delta、design、tasks | 当前规格与一次变更分离，完成后归档合并规格 |
| [Kiro](https://kiro.dev/docs/specs/quick-spec/) | `.kiro/specs/<feature>/requirements.md`、`design.md`、`tasks.md` | 用户故事/EARS验收、技术设计、实施任务 |

采用规模不能用 GitHub stars 替代。公开研究
[SpecMine v1.0](https://arxiv.org/html/2608.25202v3#A5) 的 **2026 年 7 月公开 GitHub 样本**
记录 Kiro 12,910、Spec Kit 10,619、OpenSpec 8,926 个仓库；作者将这三者列为
开发者采用的领先工具。文件名/目录指纹、模板副本及各样本重叠构成限制，
这些数字不是今天全行业的市场份额，也不能证明某种格式唯一最主流。

本项目的接入判断：先识别目标开发仓库已有的 spec 约定，保留其需求、设计、
任务的职责与目录结构。在对应内容处用普通 Markdown 链接关联设计原文、
artifact、记录位置及设计版本，补清相关行为、异常和验收依据；不把原型或
KAG 推导直接改写成已确认需求，不把全部设计文件一次性塞入 spec。
设计变更只更新受影响的需求和链接，并明确版本变化；由原 Bundle 正常发布
权威设计源，不让开发 spec 反向静默覆盖设计文件。

目标仓库没有既有约定时，`compose_spec` 使用 Spec Kit 的
`spec.md`、`plan.md`、`tasks.md` 组织；已有约定仍优先。普通开发简报也可以
使用普通 Markdown，并在写入前确定目标位置。规格由 Agent 实际编写，
不是自动导出，也不要求或授权安装这些工具。
接收 Agent 会优先识别目标仓约定并组织来源链接。完成一项交接后，可按本页的
[交接核验步骤](#验证一次完整交接)检查来源、实现与反馈回流；仅生成简报并不代表实现完成。

## 给接收 Agent 的入口

使用 `/yugoo compose_spec [功能范围]`，或直接说“把当前设计整理成开发
Spec”。主 Agent 将调用共享 `design_command` 的 `compose_spec` action，
取得当前项目、Kit pin、发布 checkpoint 与任务指导，再实际读取相关设计和
artifacts，在已授权的代码工作区生成或更新 Spec。现有规范优先；没有既有
规范时采用 Spec Kit 的 spec/plan/tasks 组织，不创建专有格式。
这是 Agent 执行入口，不是点击后立即自动导出的文件；只有实际写入并检查
后才报告生成完成。单独生成 Spec 不授权开始编码，也不修改 Design Files。
所有其他项目命令同样可由清楚的自然语言意图触发，不要求用户记住命令语法。

提供设计项目的位置、一个具体开发目标、代码工作区，以及这份指南。不要先
把全部设计文件塞进对话，也不要只说“按项目生成应用”。例如：

> 请使用这个设计项目，为“团队成员提交一项申请并查看处理结果”准备开发
> 简报。先确认相关对象、权限、流程、业务规则和页面反馈，以及哪些决策已
> 被用户确认。指出影响实现的未决问题，等我确认简报后再修改代码。

这里的申请仅是任务范围示例，不是要求任何 Kit 具有申请模型。接收 Agent 应
使用当前 Kit 的实际契约和记录，不能套用 Web App 的文件名或字段。

宿主负责 Agent、读写权限、模型与搜索。已有项目不需要重新运行所有 Bundle、
强制刷新 KAG 或先达到某个评分，才允许开始一项范围明确的开发任务。

## 接收 Agent 的工作顺序

1. **确定来源。** 用已安装集成的项目入口打开或确认指定项目，核对项目根、
   Kit 名称和版本、已发布检查点。使用宿主提供的读取能力查看工作区差异；
   把尚未发布的修改与检查点内容分开，不把二者悄悄混成一个版本。
2. **按任务找资料。** 阅读 Kit 的目录、相关 Bundle 的方法与数据契约，再找
   该操作涉及的记录和 artifact。围绕参与者、对象、输入输出、权限、状态
   变化、规则、异常与可见反馈形成最小但连贯的资料集；缺失的信息明确列出。
3. **使用 KAG，但核对原文。** 如果宿主提供知识上下文或查询入口，先取得
   实际项目、检查点和知识版本，再进行范围明确的查询或一跳关系查询。
   分页保留同一组版本和过滤条件。相关性与推导关系只是查找线索，仍要读取
   对应原文。若 KAG 不可用、过期或只覆盖一部分，说明限制并继续按任务读
   文件；不要把查询不到当作需求不存在，也不要凭空填写版本参数。
4. **先交简报。** 写出下面的信息，把影响实现的缺失决策交给用户。普通
   Bundle 正式发布的 canonical 内容是当前设计依据，不把所有已落盘设计
   再变成一轮待审批草稿。问答类内容按其实际回答字段和契约判断是否已回答。
   KAG 推导、对话中的候选建议、体验假设或评分不能替代设计源中的决定，
   也不能据此编造额外的“用户亲自确认”记录。只追问与本次任务有关、确实
   缺失或冲突的关键决策，不重新询问已有明确设计依据的事项。
   行为、范围及约束已经明确时，路由参数形式、文件组织、技术栈等普通实现
   细节由 Agent 提出合理默认并说明理由，不自动升级为必须由用户决定的问题。
   若某项技术选择涉及现有工程兼容性、外部成本、安全或部署约束，则先核对
   实际限制，仅在确实需要新决定时询问。实现范围的确认仍不可省略。
5. **只实现授权范围。** 获得用户确认后，在指定代码工作区实现并运行相关
   检查。把实际观察与未运行的检查分开。不要用代码补丁直接修改设计文件，
   使设计看起来已经支持刚实现的行为。
6. **回传差异。** 如果实现暴露设计缺口，提供来源位置、实际行为和需要的
   决策，经用户确认后由原负责 Bundle 修订并通过既有验证、发布流程保存。
   对照新检查点更新简报，并重跑受影响的代码验收；不要只改简报或体验稿。

不同宿主的项目入口与工具名称可能不同。本流程不要求用户运行 DSH 命令，
也不要求 Coding Agent 使用 Codex transport。以已安装适配提供的真实接口
为准；不要为了执行本指南而臆造工具或修改宿主配置。

## 简报应足够短，但能据此开发

简报可以使用普通 Markdown；无需新增一个持续同步的设计 JSON。至少包含：

- **本次目标与不做的事**：一次可观察的用户操作，明确开发边界。
- **来源版本**：项目、Kit pin、设计检查点，以及单独披露的未发布差异。
- **依据**：相关文件路径、记录 ID 或 JSON pointer、必要 artifact；KAG
  使用的版本和覆盖限制。引用一张原型图不能替代权限或业务规则。
- **决策与问题**：当前 canonical 设计决定及其来源、明确的用户补充决定、
  源内容之外的候选建议、暂定假设、冲突和缺失决策。无法确认来源的内容
  不能标成“用户亲自确认”；这不要求重新审批普通 Bundle 的已发布内容。
- **行为**：正常路径、重要异常、状态变化与用户可见反馈，不只是功能标题。
- **验收**：给定条件、执行动作、预期结果；包括相关的权限、失败与边界情况。
- **确认点**：哪些问题必须由用户先决定；哪些实现细节已获授权由 Agent 处理。

不要求每份简报填满固定表格。依据不足时应缩小结论、说明缺口，而不是为了
填满内容编造行为。确认简报不意味着项目中其他所有设计也同时获批。

## 怎样判断交接有效

一个没有原对话的 Agent 应能解释这项操作为什么存在、根据什么实现、哪里
仍不确定；用户应能在编码前纠正关键误解。实现结果要能对照简报逐项展示
真实测试或观察，而不是只报告“已生成”。

发现设计差异时，回传信息可以很简单：

> 来源：[文件、记录或 artifact，设计检查点]。
> 本次任务：[操作与范围]。
> 观察：[代码行为或测试结果，注明是否实际运行]。
> 缺口：[设计遗漏、冲突或不可实现之处]。
> 待决定：[选项与影响，请用户确认]。

体验视图、开发简报和实现代码都是设计的使用结果，不会自动变成新需求。
只在设计权威源按既有 Bundle 流程更新后，才把相应简报标为针对新版本。

实现授权、执行权限和产品决策由用户及宿主控制；本指南不授予发布、部署或
修改用户现有项目的额外权限。

## 验证一次完整交接

验收必须使用同一已安装发行候选，而不是只测试这份指南或模拟 Agent 输出。
选择一个实际设计项目中已有依据的纵向操作，使用隔离代码工作区，并开始一段
没有原设计对话的新 Coding Agent 会话。接收方仅获得项目位置、开发目标、
代码工作区和本指南；不预先注入答案或代替它整理全部设计资料。

1. 记录已安装发行候选的包名、版本、发行包 SHA-256 和实际安装位置，以及
   宿主版本、项目与 Kit pin、初始设计检查点；不能仅记为“最新版本”。保留
   新会话的输入范围；若使用知识上下文，记录本任务实际返回的来源、版本和
   内容范围，披露是否包含原设计对话或预先整理的答案。无法确认其来源时，
   本次验收不使用该知识上下文，改读设计源文件。Agent 按真实接口读取相关
   资料并给出带来源的简报。
2. 确认简报与本次代码修改范围。实现至少一个可执行的正常路径和一个相关
   权限、异常或边界路径，保留实际测试命令、退出码和可观察结果。
3. 选取实现中暴露的真实设计差异；若没有自然出现的差异，明确提出一个受控
   的需求变更，不伪称发现缺陷。由用户决定，再通过原 Bundle 的验证和发布
   路径更新设计，记录新检查点，而不是直接改设计文件使测试通过。
4. 接收方重新读取新版本，更新受影响的简报与实现并重跑相关验收。再次记录
   已安装发行候选的上述身份，确认与步骤 1 相同；Bundle 发布改变的是设计
   检查点，不应悄悄切换插件安装版本。若必须更换发行候选，从步骤 1 重新
   验收。保留前后安装身份、设计来源、知识上下文记录、代码差分和测试结果，
   使反馈回流能够被独立复查。

任一步未执行都须标为未完成。脚本化模型替身、源码单元测试、MCP 工具发现、
已有原对话的 Agent 或只生成开发简报，均不能单独证明这个闭环通过。验收记录
应脱敏，不把用户项目、凭据或完整宿主会话作为公开示例直接导出。

相关契约见[架构基线](system-design-baseline.md#design-to-development-handoff)。
