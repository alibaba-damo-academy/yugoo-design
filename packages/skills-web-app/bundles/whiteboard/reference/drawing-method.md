# Compose a readable, editable whiteboard

## Start with the explanation

Identify the question the drawing should answer and the intended reader. Extract
the main relationships, then choose a dominant reading order. Distinguish what
the user supplied from hypotheses. Neither a missing branch nor an empty row
authorizes inventing a business rule, emotion, metric or product feature.

Choose a starting arrangement; these are options, not a required taxonomy:

| Meaning | Useful arrangement | What carries the meaning |
| --- | --- | --- |
| Stages of an experience | Columns by stage, aligned rows for actions/support/problems | Alignment connects supporting notes to the stage; arrows only for actual transitions |
| A decision or causal process | Main path with branches in reserved side space | Label the branch condition and direction |
| Components and their interactions | Clusters by responsibility or boundary | Connect named endpoints; label what crosses a boundary |
| Categories or exploration | Spatial clusters, headings and loose notes | Proximity and containment; no obligatory arrows |
| Alternatives and tradeoffs | Shared comparison rows or columns | Comparable criteria, explicit unknowns |
| Recurring feedback | Main path plus a separate return corridor | The return destination and the reason for returning |

Do not force an open brainstorming canvas into a flowchart. Do not add a
sentiment curve merely because a drawing is called a user journey. Use such a
curve only when the input actually supports it. Follow a user's chosen visual
style even when it differs from these defaults.

## Allocate space before drawing details

Reserve regions for the main story, supporting annotations and returns. Estimate
text sizes before choosing node dimensions. Pick a readable base font and a
consistent spacing unit, then reuse them across related elements. In a new board,
roughly 18–24 scene units for primary labels is a useful starting point, not a
guarantee of readability at the eventual zoom.

Use a small, meaningful vocabulary of shapes. A diamond should indicate a
decision, not simply make a problem note look different. Show priority through
placement, size and restrained emphasis. Color can distinguish roles, but text
and position must communicate the same distinction without color.

Keep explanations near the thing they explain. A stage-aligned support note does
not need another arrow just to repeat that association. Keep a legend outside the
main routes, and omit it when direct labels already explain the visual language.

When the board becomes hard to scan, first shorten labels and remove redundant
connections. Then use an overview with detail regions on the same topic board.
Do not silently discard requested content or create extra topics merely to meet
a fixed node budget. Element count includes text and connectors: it is not the
same as the number of ideas.

## Example: experience with supporting systems

For a research journey with phases, assistance and return paths:

- Place the phases in reading order across the main row.
- Align assistance notes beneath their phases; reserve a separate band for
  shared tools if needed. Use headings rather than a connector from every note.
- Route genuine feedback outside the occupied rows, with the destination and
  trigger visible. If several returns dominate the overview, put their detail
  in a nearby region rather than drawing long crossing diagonals through it.

This is a composition example, not a required set of research phases or features.
The same approach works for onboarding, purchasing or incident handling.

## Review as a reader, then as an editor

At overview zoom: can the reader find the starting point, main story and emphasis?
At readable zoom: can they trace each important relationship without guessing?
Check clipped labels, unrelated line crossings and dense annotation blocks.
Review meaning as well as shape: a visually neat arrow in the wrong direction is
still wrong. Do not solve crowding by shrinking every label.

For edits, preserve unaffected element IDs, positions and user styling. Group
objects that should move together (for example a local annotation), not all
stages just because they share a category. Native text/arrow bindings provide
relationships; visual proximity alone does not create an editable binding.

The final handoff should name the topic, explain any material assumptions and
state whether the rendered result was inspected. Do not substitute a screenshot
or flattened image for the user's editable scene.
