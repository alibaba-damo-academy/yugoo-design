# Mindset 写作规范

语构设计系统（Yugoo Design）的设计套件（Kit）是一位领域专家的工作方式与工具箱。领域主提示词（Mindset）承载专家的人格与表达风格、思考模式、专业知识和特殊考虑，设计技能包（Bundle）提供可调用的能力；Mindset 不是 Bundle 方法的合订本。

本规范提供写作与修订依据，不增加 loader 字段、运行状态或统一工作流。创作者决定本领域需要哪些内容、采用怎样的结构与篇幅。Web App 和运筹建模的具体策略是实例，不是所有 Kit 的必选项。

## 先确定各层职责

| 位置 | 承载的内容 |
| --- | --- |
| 共享 Design Core / Panel | 用户意图优先、持续协作与保存语义、缺口驱动的通用推进指导、U/S/T、KAG/GRA、场景体验及交互基础 |
| Mindset | 领域专家的职责、风格和目标、专业判断、跨 Bundle 证据关系、特殊注意与领域边界 |
| Bundle | 一项聚焦能力的完整方法、输入输出契约、校验、交互声明、资源与修订规则 |
| Host Provider | 宿主身份、模型与工具、提问/委派和界面接入，不承载领域方法 |

现有职责与实际实现见[架构基线](../../../../docs/system-design-baseline.md)。通用的协作原则与领域的专业身份要分清：底座帮助人理解、思考、表达和对齐；Mindset 说明这个领域的专家关注什么、如何判断。可供多个 Kit 使用的调研或白板方法仍可作为独立 Bundle，不因可以复用就成为 Core 的必选流程。

## 写出对当前领域有用的增量

先读当前 Kit 的挂载与实际加载目录。`kit.yaml` 拥有精确成员关系，自动挂载提供普通技能入口；`<design_skills>` 是装载契约要求的模型侧投影，按现有作者工具维护，不能形成另一份成员权威。Mindset 正文重点回答目录本身没有说明的问题：

- **以什么专业视角帮助谁？** 说明用户已掌握什么、希望判断什么、专家的职责、个性与服务方式。身份要落到如何理解处境、思考问题和承接反馈，不止一句“你是专家”。按实际协作者调整表达，不把领域受众刻板化。
- **哪些领域知识会改变判断？** 解释重要原则、取舍、证据和不能替用户决定的事情。未知、假设、示例、观察到的事实和用户决定保持可区分。
- **哪些能力需要一起考虑？** 只补充真正重要的跨 Bundle 输入依赖、事实所有权、冲突和修订影响。说明依赖成立的情境；缺口不是强制执行许可，关系不是必经阶段。
- **有哪些例外或能力边界？** 把容易误解的特殊产物要求、外部工具依赖、真实执行与专业推断的差别讲清楚。缺求解器不等于不能建模；能展示示例不等于已经算出真实结果。
- **怎样形成有价值的互动？** 解释本领域的小闭环、何时需要用户特有信息、何时查证或提出可撤回方案，以及怎样通过具体成果帮助人判断。使用共享保存、评估、审查和场景能力，仅补本领域的适用方式。

这些是写作问题，不是要求逐项设章、为每个 Bundle 再写入口说明，或填完一张统一矩阵。少量具体例子往往比抽象要求更有效；例子不应变成隐含的强制顺序。

咨询式、执行式、探索式等都可以是专家的工作方式。Mindset 组织思考与推进，Bundle 的 handoff 决定单次执行何时交还控制；两者配合当前请求形成协作节奏。例如先连续展开多个面板形成草案，再集中审阅，同样可以保留人的控制。人格描述本身不改写运行契约。区分完整草案与已经确认的事实，真正缺少用户决定时再停下来，不用频繁确认代替有效协作。

按实际交接需要选择 Bundle 策略，不按“是否有可编辑面板”选择：`none` 可以完成成果并允许之后编辑；`must_edit` 用于成果正在等待用户输入/编辑；`user_continue` 用于先交付待确认状态，再按明确动作继续执行。具体行为见[交接契约](../../../../docs/bundle-contract.md)。要求审阅不天然等于要求修改；修改策略时同步方法、产物契约与实际交接行为，避免清单写一种、正文又要求另一种。

## 控制常驻上下文的开销

Mindset 随活动 Kit 进入主 Agent 上下文，优先放持续影响跨维度判断的信息。普通能力说明使用已有挂载目录；生成步骤、字段、脚本接口和深度专项方法放在拥有它们的 Bundle 中，需要时再读。不把所有 Bundle 的方法复制进 Mindset，也不将某次对话的临时问题积累成永久指令。

可以采用“角色与目标 → 领域判断与重要关系 → 修订及系统协作 → 边界”的组织方式，并按需要保留企业、AI、还原等专项内容。已有文件可以沿用适合领域的标题、语言和细节深度，不以统一章节数或字数作为运行条件。修订时比较前后篇幅、重复信息和每段的实际用途；短不等于好，不能用减少 token 为由删掉关键方法。

## 修订时保留原来的专业积累

编辑前建立简短保留映射：原段落/原则/案例/协议 → 保留或接收位置 → 有意修正及依据。核对专业推理、特殊依赖、例外、失败处理与事实边界，不只比对目录和标题。

只有重复的共享运行协议才考虑移往既有共享入口；先验证目标宿主、调用模式与所需阶段实际提供该内容。只在别的源码或文档看到相似段落，不算接收完成。未验证时保留，不让仓库作者规范代替安装版的运行输入。领域方法不能改写成通用“读取—生成—校验”流程。

遇到旧命令或与当前权威冲突的指令，记录原句、当前契约与获准修正；不能一面称保留，一面让互相矛盾的指令继续生效。身份、版本、精确挂载、用户字段与既有项目 pin 按原契约维护，改写 Mindset 不等于已升级用户项目。

## 用现有 Kit 对照，不照搬内容

- [Web App Mindset](../../../../packages/skills-web-app/kits/web_app/mindset.md)：观察软件产品顾问怎样处理功能、业务逻辑与页面之间的关系、Style→Page 的特殊要求、企业与 AI 场景及按需 PRD。页面和 PRD 不成为其他领域的完成终点。
- [社区工坊交付教学 Mindset](../../../../examples/community-workshop-delivery/mindset.md)：观察非软件领域怎样面向业务协调者区分已知事实、拟议应对和待确认条件，不把交付计划写成已执行事实。

涉及建模的领域仍应向业务用户解释可决策量、约束与结果，先用小范围数据验证，并区分建模、真实求解和业务采纳；不以获取内部 Kit 为前提。

交付前从目标版本的实际 loader 读取两类内容：Mindset 原文和已加载 Bundle 目录。检查身份与精确挂载保持正确，保留映射能对上正文，没有新增固定流水线或虚构能力。用与改动相称的有限情境检查选择与反馈是否连贯；源码保留、实际 Agent 行为、保存重开和安装包验收分别报告，不为纯写作修订重复全产品测试。
