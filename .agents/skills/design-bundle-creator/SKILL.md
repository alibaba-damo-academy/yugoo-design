# Design Bundle Creator

Bundle 是一个可交互、自包含的信息切片，不是一个按钮、脚本或流程阶段。先明确用户在这里理解/修改什么，以及它独占哪些 canonical 事实。

将已有 Skill 扩展为 Bundle 时，保留其专业方法和配套资源，为其中用户需要理解、比较、修改或确认的内容设计贴合任务的交互面板。提问、对话或后台执行都可能有有价值的交互对象，不能按执行形式预先跳过面板。问题与选择、变更与影响、结果与修订都可以成为表达的角度；从实际用途选择，不将聊天逐句搬成表单或添加无用字段。保存后的判断应可回看、修订并供 Agent 继续使用。确实找不到有意义的交互对象时说明具体原因，而不是仅补齐配置就声称完成了交互式扩展。

## 组合下层技能

必须读取并使用 [design-skill-creator](../design-skill-creator/SKILL.md) 及其要求的参考来编写方法/输出契约。不是仅在文档里提到技能名；在交付记录中保留这一步的实际参考和验证结果。同一 Agent 可顺序完成，不要求创建子代理。下层技能缺失时说明依赖缺口，不假称已调用。

## Bundle 层工作

1. 读取 [bundle-checklist.md](references/bundle-checklist.md)，核对目标仓库的 loader、schema、panel DSL 当前实现与同类参考。
2. 确定状态所有权、用户交互、直接依赖和 artifact 边界，再协同设计 schema/面板/输出契约。不要先生成大段方法再猜字段，也不要只做技术对象 CRUD 而丢掉专业交互。
   所有 Kit 的所有 Bundle 都遵守 [字段取舍](references/panel-authoring.md#字段取舍)：每个独立填写字段须有具体用途；一般性待确认、假设、依据与来源说明统一为可选备注，不另设通用字段组，也不只改标题。未知在备注中明确说明；真正影响方案的业务规则、约束和专用任务的核心内容保留对应表达。核对已有内容与方法契约的保留方式。
3. 创建对应 presentation profile 的固定槽位和必要资源。默认优先使用已有声明式基础组件；组件不足时明确缺口，不在 Host/Core 硬编码 Bundle 名，也不默默降级成纯文字假称可视化完成。
   编写或维护声明式面板时，读取 [panel-authoring.md](references/panel-authoring.md)，从实际运行时目录选择组件，先核对交互能力再写 DSL。
   遵循 [唯一共享基础与作者边界](references/panel-authoring.md#唯一共享基础与作者边界)：所有 Kit 使用相同的侧栏、内容框架、基础控件和编辑操作范式。作者声明业务内容、关系和已有视图选择，不逐面板调整字号、边距或按钮，不复制 CSS/控件。基础缺陷在共享层修复一次；新的信息表达需要通用能力时明确提出组件缺口。
   信息组织按目标仓库的 `docs/panel-uiux-standard.md` 判断；组件自动落实文字层级、控件和状态反馈。入口与安装版读取方式见该指南，不把场景尺寸强加给全部 Bundle。
   含画布时还须读取 [canvas-authoring.md](references/canvas-authoring.md)，统一方法的文件入口、责任边界和验证方式，不统一各 Bundle 的画布类型；沿用 `reference/`，不另建技能目录。
   有跨 Bundle 事实对齐或补充需求时，读取 [cooperation-authoring.md](references/cooperation-authoring.md)，按需编写 `reference/cooperation-guide.md` 并从方法与输出契约链接；规范只约定位置和职责，不要求补齐模板或调用全部 Bundle，不扩大写入权限。
4. 使用下层技能完成方法；用同一 fixture 验证 schema、规则、面板编辑、摘要和引用。对含产物的 Bundle 验证生成文件、引用与保存后刷新，不只验证一个空 JSON 能载入。

创建或更新 Bundle 时都要维护能体现主要用途的非空合成样例，与方法、字段和面板一起更新。声明式 Studio 预览沿用实际入口的 `reference/preview.json`，文件产物配齐可读取的有限样例资源；原生或无面板 Bundle 使用相应可验证示例，不新增统一 loader 必填槽。预览数据不得冒充实际求解、用户事实或模型执行证据。
Bundle 的职责或交互变化还要复查 Kit 挂载说明与 Mindset 的引导，用一次有限的建议、展开、反馈和修订检查顾问式体验是否连贯，不按固定顺序运行全部 Bundle。

交付前按 Panel 声明指南核对组件、section/字段的数据路径、schema 和语言资源，
让同一记录的编辑、摘要与保存指向同一 canonical 事实。内容修改通过目标宿主
实际支持的 Kit 加载/更新入口生效，须校验后发布；编辑源码或任意文件并不自动
更新已安装 Kit、打开中的面板或项目固定版本。复用已有组件的声明修改无需
重编译插件；新增共享组件实现则属于运行时构建与发布。

## 验收

Bundle 的介绍、方法和交付说明遵循[面向读者的文档原则](../design-skill-creator/references/standards.md#面向读者的文档reader-focused)：让用户或执行者能理解用途并行动，内部调试过程与验证记录不混入正常操作步骤；专业方法与必要契约仍需完整可达。

新建、修订或迁移面板时，按 [Panel 指南的面板自查](references/panel-authoring.md#面板自查)
回答信息表达是否帮助理解和思考、交互是否方便且符合习惯、信息量与组织是否便于
人工改写表达、修改结果是否支持与 AI 对齐。原则上不推荐多个内部 Tab，不把
底层集合直接拆成导航；确有独立任务或视图时说明依据及上下文保留方式。
结合代表性内容与阅读/改写路径，将结果写入现有交付记录；字段完整或结构校验
通过不能代替体验判断，不因此增加单独审批或全产品测试。

从实际 Kit loader 加载；检查资源通过运行期入口可读，样例合法，错误输入被拒绝。面板能编辑 canonical 并保存/重开，摘要反映实际内容，跨 Bundle 引用解析到真实记录。新增交互组件要做相应浏览器检查，但不为纯方法修改启动全产品 E2E。

验收必须包含与风险相称的首次生成和保存继续；只有静态/单测证据时明确尚未验证真实 Agent。已有数据不为通过测试而批量改写。

交付给 Kit 层：文件清单、选择描述、执行/handoff 策略、依赖和可选环境要求、验证证据及限制。不得把共享运行时修复、插件安装或发布当成本技能隐含授权。
