# Bundle 画布方法的文件与内容规范

本规范用于创作或修订含画布的信息切片，包括关系图、流程图、导航地图、脑图和
自由画布。统一的是资料归属、读取入口、内容边界和验收方式，**不是图形类型、
视觉风格或布局算法**。没有画布的 Bundle 不需要补文件或增加画布。

## 文件归属与读取入口

每个含画布的 Bundle 用自身的 `reference/canvas-guide.md` 作为方法入口。
沿用现有 Bundle 目录，不新增 `.skill` 目录、manifest 槽位或另一套资源读取 API。
这是系统建议的创作文件规范，不是对已有第三方 Bundle 新增的加载必需项。

| 位置 | 职责 | 不应承担的职责 |
| --- | --- | --- |
| `SKILL.md` | 领域方法及何时读取画布指南；首次设计、修订时的判断 | 复制完整画布指南、声明并不存在的组件能力 |
| `reference/canvas-guide.md` | 如何把本领域证据与事实表达为可用画布；索引已有专项方法 | 另一套 schema、运行时状态、宿主协议或事实来源 |
| `reference/artifact-contract.md` | 合法数据、引用和产物契约；链接画布指南 | 用字段清单代替生成方法 |
| `schema.yaml` / `validation.yaml` | 持久数据形状及适用阶段的机械约束 | 用风格、图数量或像素布局判定领域设计完成 |
| `panel.yaml` | 当前运行时支持的组件、数据绑定与交互声明 | 任意 JSX/CSS、生成方法正文或第二套图数据 |
| Bundle 专项 `reference/`、`scripts/`、`assets/` | 本领域格式、生成/布局/校验方法与必要资源 | 绕过原有文件权限、校验和发布通道 |
| 共享 Panel / DSL 与 UIUX 规范 | 同类组件的文字、状态、操作与实际渲染能力 | 依据 Bundle 名硬编码领域方法或要求所有画布同形 |

`SKILL.md` 链接 `reference/canvas-guide.md`；契约从同目录链接 `canvas-guide.md`。
若简单 Bundle 的输出契约原本内联，须先确认其还原入口如何读取共用画布约束，
不能仅在正向正文加链接就声称还原可达。当前仓库的显式还原入口会提示读取
`reference/artifact-contract.md`，不注入正向 Skill Body。
运行时读取仍使用 Bundle 已绑定的资源路径，而不是作者机器上的绝对路径。

已有 `bpmn_authoring.md`、`task-to-page-method.md`、`drawing-method.md` 等专项资料
保留为唯一详细来源，由指南说明何时读取；不得复制全文后维护两个版本。
一个 Bundle 有多种画布时，用同一入口分流到各自方法。不要为了统一文件名删掉
旧方法，或强制所有内容改成相同章节、相同长度。

## 画布方法需要回答的问题

以下是覆盖要求，允许交叉引用已有 Bundle 资源，不是七个必填表单或固定标题。

1. **表达什么、为什么用这种图？** 明确用户要理解或作出的判断、表达范围、
   选用的图形语义。流程顺序、实体关联、继承、依赖和自由批注不能混为一谈。
2. **事实从哪里来？** 指明 canonical 文件/集合/字段、稳定 ID、引用端点和
   条件性产物。区分从记录投影的图、需生成的文件型图、持久布局和临时视图状态。
   名称相同不建立同一身份；图和详情不得维护两套业务事实。
3. **如何生成和修订？** 给出从本领域证据选择节点、关系、分组、标签和粒度的
   方法，而非只说“生成美观图”。解释设计可提出什么、还原只能恢复什么，以及
   局部修订应保留哪些用户编辑、ID、未受影响产物与来源。
4. **谁负责布局和可读性？** 明确自动投影由共享运行时布局，还是 Agent/既有
   脚本生成 artifact 几何。说明领域特有的阅读方向、分区、标签与避让要求，
   防止文字遮挡或截断关键含义。只引用适用的共享规则：React Flow 节点端口
   约定不能强加给 BPMN 或自由白板。没有坐标契约时不能让 Agent 发明坐标字段。
5. **如何处理未知、缺失和密集关系？** 不为填满图而编造对象、连接或状态；
   区分未知与不存在。说明缺端点、缺产物、外部资源不可用和密集图时的真实
   表达/诊断方式；不能丢失既有事实来换取整齐，也不能伪造执行成功。
6. **用户能做什么、如何保存？** 按实际组件说明选择与详情联动、允许的编辑、
   只读边界、切换/刷新以及保存后的结果。点击、拖拽或双向连线只在已实现时
   承诺；使用现有 canonical/产物原子保存路径，不新增保存权威。
7. **怎样验证？** 链接有意义的合法示例及适用校验入口，明确示例不是用户事实。
   选择相关失败例（如缺失端点、非法引用或无效 artifact），区分结构校验、
   实际渲染/交互、持久保存重开与真实 Agent 生成质量，不以其中之一代替其他。

共享 UIUX 细节以目标运行时的 `docs/panel-uiux-standard.md` 或组件发现接口
返回的同包 `sharedStandards` 为准。执行者需要的领域约束必须写入 Bundle 可达
资源，不能只链接仓库开发文档。产品图形的配色/风格由其表达任务决定；工具栏、
状态提示等公共控件才复用对应共享规范。

## 交付与核验

- 先列出原方法的保留映射；仅增加入口/索引时保持原文不动。冲突条款按当前
  owning contract 和已授权范围显式纠正，不能把旧要求与新要求同时当权威。
- 经实际 Kit loader 检查指南及链接的专项资源在 `kit.resources` 内可读，分别
  从普通方法和还原契约追踪入口。不要只验证源码文件存在或 Markdown 链接拼写。
- 示例用当前 schema/validation 检查；有交互或渲染改动才做相应浏览器及保存
  检查。纯方法整理不要求重跑所有面板，也不据此声称原生 Agent 或安装包通过。
- 新能力尚未接线时明确标为待实现，不把 HTML 原型、愿景图或静态例子写成
  当前 Bundle 的运行承诺。保留不同画布的领域差异，不借规范化重设计其他切片。
