# 跨 Bundle 协作方法的文件与内容边界

这是按需内容组织规范，不是新增运行时文件槽位。只有当本领域依赖其他设计
切片、或本次设计会带来需要对齐的补充时，才在 Bundle 内编写
`reference/cooperation-guide.md`。没有需求不加占位文件，不要求填写全部章节，
也不要求依次调用所有 Bundle。

## 信息应放在哪里

| 位置 | 职责 |
| --- | --- |
| `SKILL.md` | 本领域完整方法与何时读取协作说明；不靠仓库规范替代安装后的方法输入 |
| `reference/cooperation-guide.md` | 本领域实际的相关事实 owner、触发条件、证据输入、最小补充/冲突判断和回交边界 |
| `reference/artifact-contract.md` | 合法数据表达与还原共用边界；链接协作资源，使实际还原入口可达 |
| `schema.yaml` / `validation.yaml` | 已有 canonical 引用与机械校验；协作说明不新增另一份关系状态或伪造跨文件校验 |
| 当前调用方 / 目标 Bundle 的实际入口 | 根据用户授权、执行权限与当前结算/交接状态选择下一步；目标 owner 验证、发布自己的内容 |

规范约定位置、职责和检查问题，具体 Bundle 根据真实需要组织内容。不统一
相关 Bundle 列表、步骤数量、章节名或表格格式。可链接自己的既有专项方法，
不复制或删减专业判断，也不把产品里的 Agent 协作和设计 Bundle 协作混为一谈。

## 有需要时回答哪些问题

- 哪些事实由当前 Bundle 持有，哪些事实由别的 owner 持有？什么时候确实
  需要读取或补充，什么时候应保持对方不变？避免两份提示词/说明成为双重权威。
- 依据哪些当前请求、保存状态、源文件/版本、用户决定或观察进行对齐？设计
  建议、还原事实、用户确认和未知如何区分？不能因为有一个示例就补齐产品。
- 如何识别真实目标和稳定 ID，保留已有精确来源 pin，发现缺项、重复或冲突？
  缺少 owner 内容时不猜 ID，不创建空实体，不用同名证明同一事实。
- 交回调用方的最小信息是什么：受影响记录、目标 owner/已知目标 ID、证据位置、
  必要补充或待确认问题？这是结果说明，不是新增持久化状态协议。
- 当前 executor 的读取/写入、工具调用与交接边界是什么？相关性不授予写权限。
  隔离 Producer 不得写其他 Bundle 或嵌套调用另一个生成器；由主/调用 Agent
  在既有授权、结算和人在环规则下调用目标 owner。main 模式也不扩大 Bundle
  文件所有权。不绕过 must_edit，不另造保存、校验、发布或模型客户端。
- 目标缺席、未挂载、工具不可用或用户尚未确认时如何保留缺口并退回适当交互？
  不强制安装/运行所有相关 Bundle，不把指导文档当执行 receipts。
- 后续真实补充前如何重读目标当前状态、保留用户修改；结算后如何检查实际事实
  与引用？未执行、未保存、未验证的部分必须独立报告，不能用本地 schema 通过
  声称跨 Bundle 一致性或 native 执行已验证。

## 验证与保留

从普通方法和实际还原 prompt 分别沿链接读取同一 Bundle 内资源；通过真实
loader/resource 通道检查，不只直接读取开发目录。两处必须有明确的条件入口。
如果宿主没有还原通道，则报告边界，不由源码 prompt 推断所有 native host 支持。
共享作者规范不作为已安装 Bundle 的运行输入，故实际必要约束应随资源自包含。

整理已有方法前做保留映射；旧引用、字段、专业方法、失败处理与用户事实保持
可达。只按获准范围纠正与实际权威冲突的规则，不借“协作规范”删除原方法。
验证相关本地引用、未解决引用/冲突的负例、缺少可选 owner 的路径；没有新增
运行时机制时不引入新的必填 slot、DSL、状态机或完成条件。
