# Design Skill Creator

产物是 Bundle 内的运行方法，不是另一个 Codex 安装技能。已有 schema、manifest 和面板是约束；单独调用本技能不授权修改它们。

## 开始前

1. 定位目标仓库、Bundle 和本次允许修改的文件。读取其 `skill.yaml`、`schema.yaml`、`validation.yaml`、已有方法及相关面板/摘要绑定；新 Bundle 尚不存在时先明确输出契约，与调用方协同确定，而不是猜格式。
2. 阅读 [standards.md](references/standards.md)。按其中的参考选择表读取一个同类型成熟 Bundle 的方法与输出契约；文件路径相对目标仓库，不相对用户设计项目。参考不在当前仓库时报告缺口，不猜开发机绝对路径。
3. 确认当前宿主实际暴露的资源/校验/发布契约。特别区分“作者能在源码读到”与“运行方法的 Agent 能通过资源接口读到”。
4. 修订前列出已有原则、专业方法、证据边界、失败处理和运行协议的保留映射。不能把“规范化”或“去重复”当作删减方法的理由；先明确哪些内容原位保留、哪些有验证过的接收位置。

## 写作与修订

- 方法必须让一个没有上轮记忆的执行者知道：何时适用/不适用、读什么证据、拥有什么文件、如何得到符合格式的输出、如何修订、如何校验和交接。采用 [method-template.md](assets/method-template.md) 的信息结构作为起点，不要求照抄标题或段落数。
- 复杂状态将字段、枚举、引用和产物规则放入 Bundle 自己的可读资源（推荐 `reference/artifact-contract.md`），在方法入口明确要求读取。简单状态也可以内联完整说明。提供最小有意义的合法例子，注明示例不是用户事实；不要靠“检查 schema”四个字代替契约。
- 含画布时按 [画布方法规范](../design-bundle-creator/references/canvas-authoring.md) 编写 `reference/canvas-guide.md`，从正文及输出契约链接；保留原专项方法，由统一入口索引。规范统一归属与内容覆盖，不统一图形种类，也不为没有画布的 Bundle 增加占位文件。
- 有跨 Bundle 对齐/补充需求时按 [协作方法规范](../design-bundle-creator/references/cooperation-authoring.md) 编写 `reference/cooperation-guide.md`，从正文及输出契约链接。按真实需要填充，不要求空模板、全部 owner 或嵌套执行；当前 executor 仍只写自己拥有的 Bundle，补充回交调用方。
- 保存继续先核对已保存 diff 和已有状态；保持不受影响记录及稳定 ID。核查新参数是否作用到本次相关 artifacts，更新获准影响范围，未更新者明确说明。不要重放已保存修改或自行改其他 Bundle。
- 输出形状与机械规则来自实际 schema/validation；方法负责专业判断和证据质量。不要用固定问题数、分数增量、必须跑完所有切片替代判断。
- 当前仓库 DSL 的字段表可用 `node <本技能>/scripts/render-state-contract.mjs <仓库根> <schema.yaml>` 生成（只输出，不写文件，需已有 Core build）。它投影字段/required/枚举/引用，不是完整校验器；将投影纳入文档时测试其与源 schema 同步，例子另交真实 validator 验证。
- 保留专业方法、必要提问技巧、用户可理解的说明；标准化运行边界不等于把所有领域方法改成同一段通用提示词。
- 统一的是 [standards.md](references/standards.md) 的必答问题，不是章节名称、篇幅或步骤数。不强制拆成“正向设计”和“设计还原”两章；按本领域证据解释首次设计、还原已有产品和局部修订的差异即可。正文标题使用可读名称，frontmatter `name` 保留稳定内部 ID。
- 输出契约说明如何表达合法事实，不能替代如何选择证据、作出领域判断和产生设计的方法。不要将完整方法改成一个契约链接、schema 摘要或通用“读取—生成—校验”提示。
- 当前显式还原执行不注入正向 Skill Body。设计与还原共同需要的粒度、事实/推断界限、所有权、ID/来源保留和产物要求，必须随 Bundle 放在两条入口实际可达的契约/资源中；不能只留在作者规范、仓库 AGENTS.md 或正向正文。可达约束不是让还原执行做新的设计决策。
- 仅共享运行协议可考虑移至已有系统注入入口：先核对目标宿主、main/Producer、普通/还原调用和所需阶段的实际注入，交付逐条保留映射与验证证据。不能因另一文档或提示里有相似句子就删原协议；未验证的保持原位。领域原则、判断过程和失败处理不得当作通用协议移出。
- 零删减不等于让冲突历史指令继续生效。与当前 owning contract 冲突的原句需明确定位、说明权威与冲突、按获准范围处置并记入保留映射；禁止静默删改或把固定评分增量等旧指令继续复制为新规范。

## 验收与交付

从**注入的方法入口**沿资源路径读到契约/例子，不以直接打开源码代替资源可达性测试。将例子交实际 schema 与适用验证规则；另做一次新建和一次保存后修订的行为检查，覆盖本类高风险边界（问题答案、产物引用或真实执行证据）。

交付说明：修改的契约、采用的成熟参考、原则/方法/协议的保留映射、机械验证结果、行为验证及未测项。审查正文与资源 diff，逐条核对原有约束仍在且相关执行入口可达；新增情境必须标为示例，不得篡改用户事实。仅静态检查不能声称真实注入或 Agent 行为验证通过。此层把方法和可达资源交给 Bundle 创建层；它不保证面板、安装包或跨宿主运行已经通过。
