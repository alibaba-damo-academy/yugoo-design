# 补充信息与退回重新处理的可借鉴机制

## 调研概述

本调研聚焦反馈信息不足或影响说明不充分时，系统如何保留原始上下文、通知相关方并重新进入判断流程。通过分析 Linear、Asana 和 Sleekplan 的机制，提炼出可借鉴的设计思路，为工作室项目交付平台中退回补充场景提供参考。当前证据均为定性机制描述，无定量上限数据。

## 核心发现

### 1. 原始上下文与历史记录倾向于完整保留

- **观察**：Linear Triage 在信息不足时允许负责人通过评论要求补充，issue 始终保留在系统中，所有评论历史和原始上下文不会被删除或丢失。Sleekplan 同样强调多次退回场景中，每次交互应保留在同一反馈记录的上下文中，而非创建新记录。
- **来源**：[Linear Triage](https://linear.app/docs/triage)、[Sleekplan Feedback Loop](https://sleekplan.com/blog/customer-feedback-management-that-works-a-practical-loop-for-triage-prioritization-and-closure-8762)
- **对本项目参考价值**：工作室项目交付平台的退回补充流程可考虑确保事项对象不被销毁或重建，所有补充请求和历史判断依据作为同一实体的附属记录持久化，避免跨轮次信息断裂。

### 2. 退回后的事项可见性设计存在多种思路

- **观察**：Asana 社区有一条历史帖子反映 Request Changes 后任务从待办列表消失，使后续跟进困难。Linear Snooze 提供了一种替代思路：暂时隐藏但设定自动恢复条件（时间到达或新活动），既减少认知负担又防止遗忘。
- **来源**：[Asana Forum - Request Changes](https://forum.asana.com/t/approvals-request-change-should-keep-the-task-incomplete/76962)、[Linear Snooze](https://linear.app/docs/triage)
- **对本项目参考价值**：设计退回状态时可考虑区分"已解决"与"待补充"，后者可在发起人、处理人及监督方的工作台中保持可检索和可提醒状态。Snooze 的条件恢复机制可作为参考思路。

### 3. Sleekplan 强调闭环通知

- **观察**：Sleekplan 的反馈管理闭环明确将"关闭循环"定义为向反馈者通报处理结果。在退回补充场景中，这意味着每次补充请求发出、补充内容提交、以及最终判断完成时，都应主动通知所有相关方，而非依赖被动查询。
- **来源**：[Sleekplan Feedback Loop](https://sleekplan.com/blog/customer-feedback-management-that-works-a-practical-loop-for-triage-prioritization-and-closure-8762)
- **对本项目参考价值**：工作室项目交付平台可考虑在退回补充的关键节点（请求补充、收到补充、重新判断、再次退回或结案）配置通知机制，使原始反馈者和中间处理人均能及时感知进展。

### 4. 本次材料未覆盖退回循环上限

- **观察**：本次获取的材料中，Linear、Asana 和 Sleekplan 均未明确描述退回补充的次数上限或自动升级规则。本次获取的材料未涉及此维度，不代表业界没有相关实践。
- **来源**：上述三个来源的综合分析
- **对本项目参考价值**：是否需要设定退回上限及升级路径取决于工作室项目交付平台的实际情况，本次调研未提供足够证据支持具体方案。

## 关键数据

| 维度 | Linear | Asana | Sleekplan | 备注 |
|------|--------|-------|-----------|------|
| 上下文保留方式 | Issue 实体不变，评论追加 | 任务存在，状态变更 | 单一反馈记录内追加交互 | 三者均不创建新实体 |
| 退回后可见性 | 保持可见或 Snooze 条件恢复 | 一条社区帖子反映 Request Changes 后可能不可见 | 未明确说明，隐含在闭环通知中 | 仅为单条社区反馈 |
| 通知机制 | 评论触发订阅者通知 | 状态变更触发通知 | 显式"关闭循环"通知 | Sleekplan 强调主动通报 |
| 退回上限/升级 | 本次材料未提及 | 本次材料未提及 | 本次材料未提及 | 证据未覆盖 |

本次调研未获取定量数据（如平均退回轮次、补充响应时长等），上述比较均为定性机制对比。

## 调研结论

现有工具链倾向于保留原始实体并追加交互记录以维持上下文连续性，但在退回后的可见性设计上存在不同思路。Sleekplan 强调闭环通知，但实现粒度各异。退回循环的上限与升级机制在本次材料中未被覆盖，是否需要以及如何选择取决于工作室项目交付平台的实际情况。适用性方面，上述机制均面向团队协作与反馈管理场景，与工作室项目交付平台的判断-补充-重判流程具有参考价值；未解决项包括：多角色并发补充时的冲突处理、补充内容的版本化追溯等。
