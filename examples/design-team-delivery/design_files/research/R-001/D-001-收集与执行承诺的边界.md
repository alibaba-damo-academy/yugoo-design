# 收集与执行承诺的边界

## 调研概述

本调研考察外部工具中用户反馈从接收到转化为可执行工作的边界机制。Linear Triage 和 Asana 变更控制等工具在启用相应功能后提供审查阶段，将反馈接收与后续执行解耦；这些机制可作为工作室项目交付平台的参考，但不构成普遍适用的必要条件。

## 核心发现

### 1. Triage 作为可选的审查缓冲层

**观察：** Linear 在启用 Triage 的情况下，将来自 Slack、Sentry、Zendesk 等外部集成或非团队成员创建的 issue 默认路由至 Triage 收件箱，而非直接进入团队工作流。Triage 负责人可执行 accept、decline、mark as duplicate 或 snooze 操作；accept 后 issue 进入团队默认状态和后续工作流。Linear 也提供自动化规则可跳过人工审查，因此 Triage 并非所有外部反馈的必经环节。

**来源：** [Linear Triage](https://linear.app/docs/triage)

**对本项目参考价值：** 工作室项目交付平台可参考类似的审查门槛设计，避免客户原始反馈未经判断即转化为开发任务。Triage 的四种处置动作（接纳、拒绝、合并、暂缓）可作为本项目反馈分类的操作集参考。

### 2. 客户反馈通过结构化关联保留上下文与可追溯性

**观察：** Linear Customer Requests 功能允许将客户反馈（来自 Intercom、Zendesk、Front、Asks）与具体 issue 或 project 关联，同时保留原始来源信息。支持从客户页面回溯查看所有历史请求，确保反馈不脱离其业务上下文。这种关联是显式的、双向可查的，而非依赖标签或自由文本。

**来源：** [Linear Customer Requests](https://linear.app/docs/customer-requests)

**对本项目参考价值：** 本项目可考虑建立反馈到交付物的显式关联机制，使每条被接纳的反馈都能追溯到原始客户请求及对应的交付物或范围条目。这为后续判断反馈是否属于已有交付范围提供数据基础。

### 3. 影响评估作为承诺转化的前置决策门控

**观察：** Asana 变更控制文章建议的五步流程为发起、评估、分析、实施、收尾（initiation → assessment → analysis → implementation → closure），其中评估和分析作为独立步骤置于实施之前。该文章建议将所有变更请求——包括最终被拒绝的——记录在变更日志中。这是该文章提出的流程建议，不是 Asana 产品的强制行为。

**来源：** [Asana Change Control Process](https://asana.com/resources/change-control-process)

**对本项目参考价值：** "评估影响"步骤可作为本项目中判断反馈是否属于已有交付范围的参考依据。变更日志的全量记录也为后续回溯提供数据基础。

## 关键数据

| 维度 | Linear Triage | Linear Customer Requests | Asana Change Control |
|------|---------------|--------------------------|----------------------|
| 反馈入口 | 外部集成 / 非成员创建 | Intercom / Zendesk / Front / Asks | 变更请求提交 |
| 审查机制 | Triage 收件箱 + 四选一操作 | 关联至 issue/project + 来源保留 | 文章建议的五步流程（发起→评估→分析→实施→收尾） |
| 承诺转化条件 | accept 后进入团队工作流（启用 Triage 时） | 关联至 issue/project，保留来源上下文 | 影响评估通过 + 正式决定 |
| 未转化反馈处理 | decline（附说明）/ snooze / duplicate | 保留原始记录，不强制转化 | 文章建议将拒绝请求也记录至变更日志 |
| 可追溯性 | Triage 操作历史 | 客户页面全量请求回溯 | 变更日志全量记录 |

注：本次调研未获取定量数据（如转化率、平均审查时长），上述比较基于各工具公开文档描述的定性机制。

## 调研结论

**证据支持的结论：** 以下三种机制在不同工具中被采用，可作为工作室项目交付平台的参考选项：（1）审查阶段（如 Linear Triage）在启用后将外部反馈与团队工作流解耦；（2）结构化关联（如 Linear Customer Requests）将反馈锚定到具体 issue/project 并保留来源上下文；（3）影响评估（如 Asana 变更控制）作为判断反馈是否属于已有交付范围的参考步骤。这些是可选的设计参考，不构成普遍适用的必要条件。

**适用性：** 上述机制适用于工作室项目交付平台中需要区分"客户反馈"与"团队承诺"的场景，特别是多来源反馈汇聚、交付范围约束明确的环境。Triage 模式适合高频低门槛反馈入口，变更控制流程适合范围变更决策。

**未解决项：** （1）各工具未披露反馈从接收到完成审查的平均时长及积压阈值，无法为本项目设定 SLA 提供基准；（2）Customer Requests 与 Triage 在同一组织内如何协同（例如关联后的 issue 是否仍需 Triage）未在文档中明确；（3）自动化分类（如 AI 预筛）在这些工具中的实际效果缺乏公开验证数据，本项目若引入自动化需谨慎评估误判风险。
